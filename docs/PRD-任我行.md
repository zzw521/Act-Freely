## 0. 阅读说明

### 0.1 本文的地位

本文是任我行产品需求的唯一权威来源。此前的产品定位、功能清单、能力台账、缺口盘点、云端方案、UI 对齐规格与工作台交互规格，均已合并进本文或配套的缺陷文档。

代码与本文冲突时，以代码的实际行为为准，并回写本文；本文与缺陷文档冲突时，以本文定义的产品意图为准。

### 0.2 状态图例

每个需求都标注实现状态，避免把"有入口"当成"已交付"：

| 标记 | 含义 |
| --- | --- |
| **已实现** | 代码完整，主链路在本机可运行并通过测试 |
| **有限实现** | 主链路可用，但有明确的能力边界或覆盖缺口 |
| **未验证** | 代码已写，但缺少真实外部条件（企业凭据、云资源、跨平台设备）验证 |
| **未实现** | 仅有占位、文档或规划，没有可运行链路 |

| 级别 | 定义 |
| --- | --- |
| P0 | 没有它产品无法对外交付，或会造成安全 / 数据事故 |

## 1. 产品定义

### 1.1 一句话

**任我行是一个本地优先的 AI 办公工作台：把"说需求 → 出计划 → 动手做 → 交产物"收进同一条可核查的链路，产物是真实文件，而不是一段聊天回复。**

### 1.2 要解决的问题

1. **聊天工具不交付结果。** 用户拿到的是文字建议，仍需自己打开 Office、排版、导出、拼图。
2. **云端 Agent 不让人放心。** 文件、会话、密钥默认上传，个人与中小企业缺少"数据留在本机"的选择。
3. **执行过程是黑盒。** 工具调用了什么、改了哪些文件、花了多少钱，用户看不到，也无法中途叫停。
4. **模型被平台锁定。** 用户无法按任务选择模型，也无法把本地模型和自有 API Key 接进来。
5. **办公场景被通用 Agent 忽略。** 中文文档、演示文稿、表格看板、设计原型缺少端到端的产物处理。

### 1.3 产品原则

| 原则 | 含义 | 对设计的约束 |
| --- | --- | --- |
| 本地优先 | 会话、知识、记忆、产物默认留在本机 | 云端只承载账号、市场与协作，不接触对话与文件内容 |
| 产物导向 | 每轮任务尽量落到可打开、可继续编辑的文件 | 不以"回复长度"衡量完成度，以产物与验收结果衡量 |
| 执行可核查 | 计划、步骤、工具、审批、用量全程可见 | 高风险动作必须显式授权；失败必须中文可见 |
| 模型可选 | 云端模型、OpenAI 兼容端点、本机 Ollama 均可 | 不绑定单一厂商；密钥进系统钥匙串 |
| 诚实降级 | 做不到的能力明示"尚未提供"，不静默成功 | 未接入、未验证、平台不支持，都必须在界面上说清楚 |

### 1.4 目标与非目标

**目标**

- 让个人用户在一个窗口内完成"对话 → 计划 → 执行 → 产物 → 继续修改"。
- 让中小企业可以在不把数据交给第三方的前提下，使用具备执行能力的 AI 工作台。
- 让能力扩展（技能、专家、连接器、市场）可安装、可审查、可撤销。
- 让执行面（终端、浏览器、桌面、远程桌面）在明确授权与审计下可用。

**非目标**

- 不做通用大模型训练与推理平台。
- 不做面向消费者的 IM 社交产品。
- 不承诺跨平台操作系统级沙箱：Windows 已提供 AppContainer 隔离，macOS / Linux 目前只有策略沙箱。
- 不在 1.0 前做大规模多租户 SaaS 与计费系统。
- 不追求与 OpenHuman 相同的"单机数百 Agent"吞吐指标。

### 1.5 目标用户

| 画像 | 典型身份 | 核心诉求 | 主要场景 |
| --- | --- | --- | --- |
| 独立知识工作者 | 咨询顾问、运营、市场 | 快速出报告、方案、演示稿 | 周报、竞品分析、提案、培训材料 |
| 设计与产品 | 产品经理、UI / UX | 从需求直接得到可交互原型 | 需求澄清、页面原型、方案对比 |
| 中小企业团队 | 3–50 人团队负责人 | 数据不出内网、成员可协作 | 项目协作、资料沉淀、任务分派 |
| 技术型用户 | 开发者、运维 | 可控的终端与浏览器执行 | 脚本执行、网页操作、环境排查 |

### 1.6 核心 Job To Be Done

1. 当我要交一份材料时，我希望只描述目标，就得到能直接打开的文件，而不是一段需要自己排版的文字。
2. 当任务会改动文件或执行命令时，我希望先看到计划，并能随时终止，或改写提问后重跑。
3. 当 company 禁止数据出域时，我希望会话、知识库与产物留在我自己的机器上。
4. 当某个模型效果不好或太贵时，我希望按任务切换模型，并看到每次调用的成本。
5. 当团队要复用一套做法时，我希望把它沉淀成技能或专家套件，而不是每次重新写提示词。
6. 当我在 IM 里收到需求时，我希望同一个 Agent 能在频道里接单并把结果回报到项目。

### 1.7 成功度量

| 维度 | 指标 | 0.1.0 目标 | 1.0 目标 |
| --- | --- | --- | --- |
| 激活 | 首次启动完成模型配置的比例 | ≥ 60% | ≥ 75% |
| 任务 | 单次会话产生至少一个产物的比例 | ≥ 35% | ≥ 55% |
| 产物 | 产物被再次打开或继续编辑的比例 | ≥ 25% | ≥ 40% |
| 可靠性 | 任务成功率（无引擎错误、无审批死锁） | ≥ 90% | ≥ 97% |
| 信任 | 用户主动开启执行面的比例 | 观测 | ≥ 30% |
| 效率 | 从提交到首个产物的事件时延（P50） | ≤ 90s | ≤ 45s |
| 成本 | 单任务模型成本中位数 | 观测 | 较 0.1.0 下降 30% |

## 2. 竞品与差异化

### 2.1 Octop（腾讯云开源）

- **许可证与形态**：MIT；Python 3.12+ / FastAPI 单进程，无消息队列；SQLite WAL 或 PostgreSQL；React 18 + TypeScript + Vite + Ant Design；桌面端为 Wails v3（Go）壳内嵌可移植运行时。
- **核心能力**：多用户 JWT、用户组、专家库与市场、AgentTeams（Beta；主持人 + 成员、群聊时间线、异步派工）、LangGraph 执行内核、10 类 IM 通道（飞书、钉钉、QQ、企业微信、微信 iLink、元宝、小艺、MQTT、Telegram、Discord）、MCP/OAuth、知识库 RAG、插件、ACP 双向、终端 / 浏览器 AI+ / 远程桌面、cron、多种 workspace 后端（本地 / Docker / PG / COS / S3）。
- **优势**：服务端优先、多用户与团队协作完整、IM 覆盖广、RAG 成熟、部署形态多； MIT 许可允许闭源商用与再分发。
- **弱项**：桌面端本质是把完整服务塞进本地，体积与资源占用偏高；产物型办公（设计稿、PPTX、DOCX）不是主线；AgentTeams 仍在 Beta；单进程无队列，横向扩展与高可用受限。
- **活跃度**：约 1.1 万 star；最新 v1.0.3b1（2026-10-25）；仓库创建于 2026-07。

### 2.2 OpenHuman（tinyhumansai）

- **许可证与形态**：GPL-3.0（核心与 tinyagents / tinyflows / tinycortex / tinychannels 同为 GPL-3.0）；Rust 单进程、可嵌入库；Tauri v2 + React 19 桌面应用，另有终端与无头服务。闭源产品不能拷贝其代码，只能借鉴设计。
- **核心能力**：面向 Agent 舰队的轻量 harness（宣称 $10 VPS 跑 500 个 Agent）、RLM 工具结果压缩、Jev 工具检索、统一 Rust 总线、内置记忆引擎（Markdown 为源、SQLite 派生索引）、语音 Agent、浏览器与桌面控制、119 个 OAuth 集成（Composio）、14 个消息通道（WhatsApp 未随包发布）、可视化工作流、审批门、OS jail / Docker 沙箱、隐私模式、系统钥匙串、按次用量统计。
- **优势**：性能与资源效率、可嵌入、集成生态、语音、工作流、跨平台；桌面端单用户，多租户仅由 Embed 的 `ProfileRuntime` 提供。
- **弱项**：GPL-3.0 不适合闭源商业分发；办公产物不是核心；中文生态与企业协作较弱；仍处 Early Beta（0.x）。
- **活跃度**：约 4.2 万 star；最新 v0.64.15（2026-10-09）；仓库创建于 2026-02。

### 2.3 三方对比

| 维度 | 任我行 0.1.0 | Octop | OpenHuman |
| --- | --- | --- | --- |
| 许可证 | Apache-2.0 | MIT | GPL-3.0 |
| 首要形态 | 桌面端（Tauri） | 服务端 + Wails 桌面端 | 桌面端 + Rust 库 |
| 执行内核 | Rust harness（普通任务）+ Python（FastAPI + AgentScope，重能力） | Python（LangGraph） | Rust |
| 本地优先 | 强（默认本地数据根） | 中 | 中 |
| 多用户 / 租户 | 未实现 | 已实现 | 有限（ProfileRuntime） |
| 团队协作 | 有限（10 秒轮询） | 已实现 | 未实现 |
| 办公产物 | 中（HTML / PPTX / Markdown；XLSX / DOCX 未实现） | 中 | 弱 |
| 工作模式 | 通用 / 设计 / 幻灯片（写作可选） | 通用对话 | 通用对话 + 工作流 |
| 专家 / 团队 | 专家套件 + 专家团队（有限） | 专家库 + AgentTeams（Beta） | 多 Agent（库级） |
| 技能 / MCP | 已实现 | 已实现 | 已实现 |
| 在线市场 | 已实现（签名 + TOFU） | 已实现 | 未实现 |
| IM 通道 | 4 个（仅文本、未验证真实凭据） | 10 类 | 14（WhatsApp 未发布） |
| 知识库 | 本地 FTS5（无向量） | RAG | 记忆引擎 |
| 执行面 | 终端 / 浏览器 / 电脑 / 远程桌面（只看） | 终端 / 浏览器 / 远程桌面 | 终端 / 浏览器 / 桌面 |
| 沙箱 | 策略沙箱 + Windows AppContainer | Docker 工作区 / 容器隔离 | OS jail / Docker |
| 语音 | 未实现 | 未见语音输入 / 实时语音（IM 可承载 audio） | 已实现 |
| 可视化工作流 | 未实现（仅 cron） | 部分 | 已实现 |
| 可嵌入 API | 未实现 | 部分 | 已实现 |
| 部署形态 | 本机直跑（Docker 模板未验证） | 桌面 / Docker / NAS / 云 | 桌面 / 服务 / 库 |

### 2.4 差异化结论

**不打的仗**

- 不与 Octop 比多租户服务端与 IM 广度；它的架构从第一天就是平台化的。
- 不与 OpenHuman 比 Rust 性能、Agent 舰队密度与可嵌入性；它的核心是 harness，不是办公产品。
- 不在 1.0 前承诺"什么都能接"的 OAuth 集成数量。

**可借鉴的交互**

- 可折叠的推理与工具活动分组：默认收起，失败时自动展开。
- 审批卡提供"批准 / 始终允许 / 拒绝"三选项，并记住授权范围，减少重复确认。
- 对话中由 Agent 提案工作流，一键保存为可复用任务；在引入画布前，先落到定时任务或专家套件。
- 记忆与知识以 Markdown 为源，可读、可迁移，避免黑盒向量库带来的合规与迁移阻力。

**空档**

Octop 强在多用户，但桌面端是把完整服务塞进本地，偏重；OpenHuman 桌面端是单用户，多租户只在嵌入式场景提供。两者之间有一个"桌面优先、数据本地、但支持小团队"的空档。任我行在 1.0 前不做多租户 SaaS，但应把"单团队本地部署 + 协作"作为差异化方向。

**要打的仗**

1. **桌面本地优先的信任感**：数据根、密钥、产物、知识库都在本机，云端只做账号与市场。
2. **中文办公产物闭环**：从一句话到可打开的 HTML / XLSX / DOCX / PPTX，并支持继续修改。
3. **可核查执行面**：计划审阅、逐步审批、终止 / 改写提问重跑、断线重放、用量台账。
4. **能力沉淀**：技能、专家套件、项目协作，把个人经验变成团队资产。
5. **诚实的产品边界**：未验证与未实现的能力在界面上明确标注，不用模板冒充交付。

- **工作台**只负责当前会话与产物，不承担系统配置。

- **模型中心**承担模型配置、路由与用量，不与设置里的"模型与用量"重复实现，后者只做摘要与跳转。

## 4. 功能需求

### 4.1 账号与首次启动

**目标**：让用户在不清空本地数据的前提下完成登录，并清楚知道哪些数据会上云。

| ID | 需求 | 优先级 | 状态 | 验收要点 |
| --- | --- | --- | --- | --- |
| ACC-01 | 桌面端通过系统浏览器完成网页验证，再经 loopback 回调登录 | P0 | 已实现 | 一次性 code + state；回调端口仅回环；失败有中文原因 |
| ACC-02 | 登录态包含昵称、头像、套餐；未登录可浏览本地功能 | P1 | 已实现 | 未登录不发云端请求；点击登录拉起浏览器 |
| ACC-03 | access token 短期、refresh token 轮换；密钥存系统钥匙串 | P0 | 已实现 | 刷新失败回到未登录；钥匙串不可用时有明确降级 |
| ACC-04 | 退出登录清理令牌，但保留本地任务、会话、产物 | P0 | 已实现 | 退出后本地数据仍可打开 |
| ACC-05 | 离线 / 服务端不可达时，登录失败必须可见 | P1 | 已实现 | 不静默成功；可重试 |
| ACC-06 | 首次启动引导：模型配置、数据目录说明、隐私边界 | P1 | 有限实现 | 有设置入口；无强制向导 |
| ACC-07 | 多账号切换 | P2 | 未实现 | 当前单账号 |
| ACC-08 | 账号注销与数据导出 | P1 | 未实现 | 需服务端配合 |

**边界**

- 账号服务只承载账号、市场与协作，不接收对话内容、文件内容与密钥值。
- 未登录状态下，市场下载与项目协作不可用，其余本地能力可用。

### 4.2 对话工作台

**目标**：一个窗口完成"输入 → 执行 → 产物 → 继续修改"，对话区保持轻量。

| ID | 需求 | 优先级 | 状态 | 验收要点 |

## 5. 关键流程

### 5.1 对话到产物

```text
用户输入需求
  → 选择工作模式 / 技能 / 附件
  → 提交任务（生成任务 ID）
  → 引擎流式返回计划（plan 事件）
  → 自动批准或用户审阅
  → 执行步骤（step 事件，含工具调用）
  → 产物生成（artifact 事件）
  → 交付摘要（done 事件）
  → 用户预览 / 外部打开 / 继续修改
```

**失败路径**

- 计划被拒绝：任务结束，不执行，保留输入以便修改。
- 工具失败：该步骤标记失败，展示中文原因；可重试或终止。
- 引擎退出：任务标记失败，提示检查引擎日志；不伪装成超时。
- 网络中断：前端按 seq 重放；恢复后继续接收。

### 5.2 计划审批与中断恢复

1. 计划事件到达后，前端展示步骤、风险等级、预计产物。
2. 低风险且开启自动批准：直接进入执行，但保留"终止"入口。
3. 高风险：等待用户确认；拒绝则终止。
4. 执行中只有"终止"：不再提供暂停/继续，用户可随时停止任务。
5. 已提交的提问可以改写：保存后作废该轮回复与之后的所有轮次，并按新提问重新执行（运行中不可改写）。
6. 进程重启后，从最近检查点恢复，并展示将重放的步骤。

### 5.3 登录

1. 用户点击登录，桌面端启动本地回环监听。
2. 打开系统浏览器到账号服务登录页，携带 `state`。
3. 登录成功后服务端 302 回环地址，带一次性 `code`。
4. 桌面端校验 `state`，用 `code` 换取令牌。
5. 令牌写入钥匙串；刷新令牌轮换；失败回到未登录。

### 5.4 技能 / 套件安装

1. 从本地目录或市场选择包。
2. 校验 SHA-256；市场包校验发布者签名。
3. 静态风险扫描；命中高风险需二次确认。
4. 解压到用户数据目录；登记来源与版本。
5. 安装后立即可引用；卸载时清理目录与登记。

### 5.5 定时任务

1. 用户创建任务，设置 cron、模型、工作区、提示词。
2. 到达触发时间，引擎启动一次隔离会话。
3. 执行结果写入运行记录；失败保留错误。
4. 用户可查看记录、手动重跑、启停任务。

### 5.6 协作任务闭环

1. 项目负责人在桌面端创建任务并指派成员。
2. 成员在本地会话执行，结果回报到任务。
3. 评论与状态更新通过轮询同步。
4. 任务完成后归档；产物仍留在成员本机。

## 6. 数据与存储

### 6.1 数据根

| 变量 | 默认位置 | 内容 |
| --- | --- | --- |
| `TONGTIAN_HOME` | `%APPDATA%\tongtian-office`（非 Windows 为 `~/.tongtian`） | 工作区、产物、模型配置、任务事件、会话 |
| `TONGTIANWORK_HOME` | `~/.tongtianwork` | 意识文件、知识库、浏览器专用数据 |
| 系统钥匙串 | 操作系统 | 模型密钥、市场令牌、IM 凭据、MCP OAuth 令牌 |

### 6.2 本地数据

本地数据有两处载体：桌面端 `{TONGTIAN_HOME}/t.db` 存任务、消息、审计、模型用量、MCP 与钩子授权等 17 张表；引擎侧的知识索引单独成库。两处都不承载账号、市场与项目数据。

| 数据 | 形态 | 生命周期 |
| --- | --- | --- |
| 会话与消息 | JSON / SQLite | 用户删除或归档 |
| 任务事件 | 追加日志（带 seq） | 随会话保留；可重放 |
| 产物 | 工作区文件 | 用户管理 |
| 知识库 | SQLite FTS5 | 用户删除集合 |
| 意识与记忆 | Markdown / JSON | 用户编辑或删除 |
| 审计日志 | 追加文件 | 用户导出或清理 |
| 用量 | 本地记录 | 随任务保留 |

### 6.3 服务端数据

服务端只有 `data/market.db` 一个库，账号、市场与项目都在里面，进程外不暴露。

| 数据 | 存储 | 说明 |
| --- | --- | --- |
| 账号 | SQLite WAL | 用户名、密码哈希、套餐 |
| 会话令牌 | 短期 JWT + refresh | refresh 轮换 |
| 市场包 | 文件 + 元数据 | 版本、哈希、签名、下载数 |
| 项目与任务 | SQLite WAL | 成员、角色、评论、结果摘要 |

**不上云**：对话内容、文件内容、知识库正文、模型密钥、IM 凭据。

### 6.4 数据生命周期

- 卸载应用不自动删除数据根；用户需手动清理。
- 退出登录不删除本地数据。
- 删除知识集合、记忆、会话必须立即生效，且有确认。
- 市场包卸载必须清理安装目录与登记，不残留可执行文件。

### 6.5 存储归属

| 库 | 文件 | 写入方 | 读取方 |
| --- | --- | --- | --- |
| 桌面端 | `{TONGTIAN_HOME}/t.db` | 仅 Rust 主进程 | Rust；渲染进程只走 IPC |
| 服务端 | `data/market.db` | 仅服务端进程 | 仅服务端 |
| 引擎 | 知识索引库、检查点目录、用量台账 | 仅引擎进程 | 引擎自身；对外只经 API 汇总 |

- 三套库禁止跨端直连：桌面端不直写 `market.db`，服务端不读 `t.db`，引擎不打开 `t.db`。
- 用量必须先落盘再聚合：桌面端已写入 `model_usage`，引擎侧目前只在进程内累计，重启即丢，不能作为计费或配额依据（见缺陷 D-43）。
- 表结构只做增量变更：新增表或新增列并回填，不删列、不改语义、不覆盖存量行。

## 7. 非功能需求

### 7.1 性能

| 指标 | 目标 | 现状 |
| --- | --- | --- |
| 冷启动到可输入 | ≤ 5s（Windows 主流配置） | 未系统测量 |
| 事件首包时延 | ≤ 2s | 未系统测量 |
| 单任务产物 P50 | ≤ 90s | 未系统测量 |
| 内存占用（空闲） | ≤ 400MB | 未系统测量 |
| 大文件预览 | 50MB 内可打开 | 已有限制 |

### 7.2 可靠性

- 引擎异常退出必须被桥接层识别，返回明确错误码，不得伪装成启动超时。
- 任务事件必须可重放，重复投递不产生重复步骤。
- 审批、授权、配额等状态变更必须持久化。
- 单点失败不得导致整个应用不可用；模型失败可切换，通道失败可重连。

### 7.3 安全

- 密钥只进钥匙串，不进配置文件、日志、构建产物。
- 非回环绑定必须同时满足远程绑定开关与令牌。
- 所有执行面默认关闭，逐项授权，可随时收回。
- 第三方包安装前必须校验完整性与签名，并做静态扫描。
- 错误信息不得包含密钥、完整令牌或用户文件内容。

### 7.4 兼容性

| 平台 | 状态 |
| --- | --- |
| Windows 10/11 + WebView2 | 主要验证平台 |
| macOS | 未验证 |
| Linux | 未验证 |
| 浏览器（仅前端） | 支持，用于调试与服务化 |

### 7.5 可观测性

- 引擎日志结构化，包含任务 ID、步骤、工具、耗时、错误码。
- 桌面端日志与引擎日志可关联同一任务 ID。
- 用量记录必须来自真实调用，不用估算值冒充。
- 审计日志覆盖工具调用、授权变更、安装卸载、登录登出。

### 7.6 可维护性

- 前后端契约集中在 `src/shared`；跨进程命令有类型定义。
- 错误码稳定，文案映射集中管理。
- 核心逻辑必须有单元测试；跨进程链路有集成测试。
- 文档与代码冲突时，先修代码或修文档，不能长期并存。

## 8. 技术架构

### 8.1 分层

```text
渲染进程（React 18 + MUI 5 + Zustand + HashRouter）
    │ Tauri IPC（invoke / event）
Tauri 2 核心（Rust）
    ├── 本地 harness（默认）：计划 → 审批 → 工具循环 → 检查点
    └── 桥接层（能力越界时）
          │ HTTP + SSE（本地回环）
Python Agent 引擎（FastAPI + AgentScope）
    │ REST
综合服务端（FastAPI + SQLite WAL）
```

| 层 | 职责 | 不承担 |
| --- | --- | --- |
| 渲染进程 | 交互、状态、预览、设置 | 进程管理、文件系统直连、密钥存储 |
| Rust 核心 | 窗口、进程、文件边界、桥接、钥匙串、系统集成；本地 harness 的 Agent 循环、模型调用、文件工具、技能取用、检查点 | 连接器、浏览器、电脑操控、知识库、负责人专家、Hooks、逐工具审批、出站脱敏、ACP |
| Python 引擎 | 上述 Rust 不承担的能力，以及 IM 长连接、引擎侧沙箱与用量 | 账号、市场、协作 |
| 综合服务端 | 账号、市场、协作 | 对话内容、文件内容、密钥 |

**执行器选择**：普通对话与文件类任务默认由本地 harness 在本机进程内完成；当本轮涉及幻灯片、负责人专家、图片附件、安全工作环境、MCP 连接器、知识库、Hooks、逐工具审批、出站脱敏或 ACP 时，整轮显式交给引擎，并在对话里以可见步骤说明原因。两类执行器共用同一套事件契约、事件持久化、用量计量与审计，渲染层不区分事件来源。

### 8.2 关键契约

- **SSE 事件**：`plan` / `step` / `artifact` / `done` / `error` / `usage` 等；每条带 `seq`，支持 `event:` 行类型。本地 harness 与引擎产生同构事件（harness 事件无 `seq`，仍经同一持久化与推送链路）。
- **任务控制**：提交、审阅、终止、改写提问后重跑、检查点查询；两类执行器的检查点分目录存放（`checkpoints/` 与 `checkpoints-harness/`），互不串读。
- **命令面**：173 个 Tauri command，覆盖系统、桥接、模型、设置、计划、文件、账号、协作、安全、技能、市场、知识、专家、执行面、MCP。
- **错误**：稳定错误码 + 中文文案；跨进程错误不得只返回裸字符串。

### 8.3 依赖与分发

- 桌面端以 Tauri 打包，Windows 产出 MSI 与 NSIS。
- Python 引擎以 embeddable Python 随包分发；缺失时应用可启动，本地 harness 仍可处理普通任务，需要引擎的能力必须明示不可用。
- 服务端独立部署，默认 SQLite WAL；不依赖外部消息队列。
- 市场包存放在服务端存储目录；客户端安装到用户数据目录。

### 8.4 已废弃的架构假设

早期规格曾规划"Rust 全栈核心 + Python 仅 sidecar"，随后实现为"Rust 壳 + Python Agent 引擎"。当前实现是"Rust 内嵌 harness 优先 + Python 引擎承接重能力"：普通任务由 Rust 完成 Agent 循环与模型调用，能力越界时整轮交给 Python 引擎。所有新需求、评审与排期以当前分层为准，不再按旧规格评估工作量。

## 9. 版本规划

### 9.1 0.1.0（当前）

**主题**：本地可用的办公 Agent。

- 已完成：对话、三种默认工作模式、产物、计划审批、终止与改写重跑、回放、模型中心、技能、专家套件、MCP、市场、知识库、意识、定时任务、执行面、Hooks、安全设置、协作、账号、服务化直跑、Windows 系统级隔离。
- 明确边界：IM 未验证真实凭据、Docker / 反代 / TLS 未验证、macOS / Linux 未验证、系统隔离只覆盖 Windows 且不含 Hooks、无多租户、无语音、无自动更新。

### 9.2 0.2（本地完整体验）

**主题**：把"能用"变成"敢用"。

- 服务化闭环：Docker 镜像、反向代理、TLS、公网 SSE 实测。
- 安全补齐：系统级隔离覆盖 macOS / Linux；审计防篡改；Hooks 纳入隔离；MCP 依赖目录的授权体验。
- 体验补齐：应用快照、更新检查、任务级预算 UI、失败步骤重试。
- 知识增强：向量检索与重排的可选实现。
- 质量：真实外部链路测试、错误处理统一、跨平台构建验证。

### 9.3 0.3（团队协作）

**主题**：从个人工具到团队工具。

- 协作实时推送（WebSocket / SSE），替代轮询。
- 团队知识库共享与权限。
- 市场自动更新、撤销列表、插件执行沙箱。
- 多账号与组织基础。

### 9.4 1.0（云端闭环）

**主题**：可运营、可计量、可扩展。

- 多租户、配额、计费、审计。
- Web 端闭环 + Runner / Gateway。
- 管理后台：成员、配额、模型、审计。
- 移动端只读与通知。

### 9.5 云端阶段与容量目标

| 阶段 | 内容 | 周期 |
| --- | --- | --- |
| Phase A | 账号同步、设备管理、基础配额 | ~4 周 |

## 11. 风险与开放问题

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| Python 引擎冷启动与内存高于 Rust 方案 | 体验落后于 OpenHuman | 预热、懒加载、上下文压缩；不以性能为唯一卖点 |
| 系统隔离仅覆盖 Windows 且不含 Hooks | macOS / Linux 与 Hooks 仍可能被质疑 | 设置页分两层如实标注；0.2 补平台与 Hooks 覆盖 |
| IM 真实凭据未验证 | 企业交付受阻 | 0.2 前完成至少一个通道的真实联调 |
| Docker / 反代 / TLS 未验证 | 服务化无法交付 | 0.2 作为发布门槛，不接受模板冒充 |
| 市场只安装不更新 | 供应链风险 | 0.3 补自动更新、撤销列表、插件沙箱 |
| 多租户缺失 | 无法服务团队 | 1.0 前不做大规模 SaaS；先做单团队部署 |
| 知识库仅词法检索 | 召回质量有限 | 0.2 评估向量检索，保留词法兜底 |
| 跨平台未验证 | 市场覆盖受限 | Windows 优先；macOS / Linux 单独立项 |

**开放问题**

1. 系统隔离在 macOS / Linux 走什么机制（seatbelt、bubblewrap、容器），是否需要与 Windows 共用同一套启动器协议？
2. 多人协作是否继续走自建服务端，还是接入企业现有 IM 与项目系统？
3. 市场签名信任模型是否引入组织级信任锚，而不是仅 TOFU？
4. 是否提供可嵌入 SDK，以覆盖 Octop / OpenHuman 的服务端集成场景？
5. 语音能力是自研还是接入系统 / 第三方？
