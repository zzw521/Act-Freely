# 运营专家分析报告

> 角色：运营专家（agent 办公系统专家团）
> 输入依据：`docs/spec/spec-通天办公-云端与账号体系.md` v1.0（下称「云端 spec」）、`docs/spec/spec-通天办公.md` v2.1（下称「主 SPEC」）、`docs/spec/spec-通天办公-占位能力清单.md` v1.0（下称「占位清单」）
> 约束基线：DAU ~50K、峰值并发会话 ~2000、模型调用限流降级、token 成本预算管控

---

## 1. 结论摘要

本产品具备清晰的运营飞轮基础：任务成功率（主 SPEC §9.3 目标 ≥85%）可作为信任锚点驱动激活，技能市场（占位清单 SkillMarket P1、主 SPEC §3.6.5）是留存与变现双引擎，组织维度的用量配额体系（云端 spec §8）天然支撑企业侧扩展。核心结论三点：① 北极星指标定为「周有效完成任务数」，50K DAU 推导目标 ≥25 万/周；② token 成本必须建立「组织-用户-agent-任务」四级配额 + 70/85/95/100% 四档阈值 + 「降级→排队→阻断」三级超限动作，现有 Gateway 计量（云端 spec §2）只覆盖组织级，属关键增量；③ 按 DAU 50K、人均 1.5 任务/日估算，平台月 token 成本约 ¥28–40 万，须设 ¥30 万/月硬预算并配预算熔断（区别于主 SPEC §3.2.4 的可用性熔断）。最大风险是埋点与数据分析基础设施在现有架构中完全缺失（占位清单 AuditView 为纯占位、云端 spec §2 无 Analytics 组件），所有运营动作的前置条件是 P0 先建指标管道。

## 2. 风险清单

| 编号 | 风险描述 | 等级 | 依据 |
|------|----------|:----:|------|
| R1 | token 成本失控：50K DAU × 1.5 任务/日 × 3 万 token/任务 ≈ 22.5 亿 token/日，月成本 ¥28–40 万；免费层遭批量注册滥用时成本可翻倍 | 高 | 云端 spec §10.2 已列「Runner 成本失控」但缓解仅为「容器池限额+组织配额+排队降级」，无用户/任务级配额与预算熔断 |
| R2 | 数据埋点与指标管道缺失：现有架构（云端 spec §2）无 Analytics/事件采集组件，占位清单 AuditView 为纯占位，任何指标目标都无法度量 | 高 | 云端 spec §2 组件表仅 Auth/Sync/Runner/Gateway/Files/Admin；占位清单 §2 AuditView「纯占位」 |
| R3 | 免费配额过紧伤害激活：20 万 token/日 ≈ 10 个任务，重度用户首日即触顶，触发阻断造成流失 | 中 | 本报告 §8.2 配额推导；主 SPEC §9.3 任务完成率目标隐含单任务多轮重试消耗 |
| R4 | 技能市场供给不足：SkillMarket 纯占位（占位清单 P1），marketplace API 在主 SPEC §3.6.5 列为 P2，飞轮冷启动无内容 | 中 | 占位清单 §2 SkillMarket 行；主 SPEC §3.6.5「后续版本 P2」 |

## 4. 待澄清问题

1. **免费层 token 配额定多少？** 本报告推荐 20 万 token/日 + 400 万/月（约 10 任务/日），理由：覆盖人均 1.5 任务/日的 6 倍余量，同时把单免费用户月成本压在 ¥6 以内。若 TL 要求更激进激活，上限可放宽到 50 万/日但需预算委员会确认。
2. **超限动作优先级是「先降级」还是「先排队」？** 推荐先降级后排队：降级保体验连续性（任务不中断），排队保公平；但该顺序会拉低任务成功率（R8），需与质量线共同确认降级模型的成功率基线 ≥80% 才可执行。
3. **北极星指标用「周有效完成任务数」还是「周活跃留存用户数」？** 推荐前者（≥25 万/周）：任务完成是价值交付的直接证据，留存是其滞后结果；但需产品侧确认「有效」口径（§6.1：done 且 24h 内无回滚且无用户差评）。
4. **平台月度 token 补贴预算上限？** 推荐 ¥30 万/月硬顶 + 日级 ¥1.2 万软顶（超软顶触发全局降级）；依据：自带 Key 用户占比目标 30%（主 SPEC §10.3 双轨设计）可对冲约 30% 成本。
5. **组织排行榜是否对企业 owner 可见成员个人明细？** 推荐仅聚合到成员级「任务数/成功率」两项，不暴露任务内容与对话明细，与云端 spec §7 审计最小化对齐。
6. **技能市场变现模式与上线时机？** 推荐 Phase C 内先做免费分发 + 安装排行，付费分成延后至 DAU ≥20K 后，避免供给不足时收费抑制安装渗透率（目标安装渗透 ≥30%）。
7. **任务成功率由谁判定？** 推荐系统判定为主（状态机 done + 无回滚），用户点评为辅（差评强制标记无效任务），纯系统口径会被「假完成」抬高（主 SPEC §9.3 的 ≥85% 需同口径校准）。
8. **企业客户扩展是否需要专属定价档位？** 推荐在现有 free/pro/enterprise 三档（云端 spec §4.2 organizations.plan）上为 enterprise 增加「配额自定义 + 专属预算告警」两项商务配置，不新增实体。

## 5. 运营抓手专项（任务 1）

每个抓手标注作用机制、依赖的现有设计、所需增量。

| 编号 | 抓手 | 作用机制 | 现有设计依赖 | 所需增量 |
|------|------|----------|--------------|----------|
| G1 | 任务成功率与交付报告展示 | 信任锚点：工作台展示个人历史成功率与「本任务节省 X 分钟」，交付产物生成可分享报告页 → 降低新用户决策成本、制造口碑素材 | 主 SPEC §9.3（一次交付 ≥85%）、§3.1.3 Deliver/Done 事件 | 时长节省估算埋点、分享页（用户端后端渲染） |
| G2 | 技能市场 + 安装排行榜 | 供需飞轮：创作者发布 → 用户安装 → 排行榜曝光 → 吸引更多创作者；安装行为本身是留存动作，优质技能是付费理由 | 主 SPEC §3.6.5 marketplace API（P2）；占位清单 SkillMarket（P1 纯占位）；云端 spec §8 资产中心 | marketplace 服务端提前建设、技能审核流程、安装计数统计 |
| G3 | 组织排行榜与用量周报 | 组织内同侪比较驱动成员活跃；管理员周报让决策者持续感知价值 → 续费率 | 云端 spec §8 用量与配额聚合 | 排行聚合任务（仅组织内可见）、邮件订阅 |
| G4 | 模板任务库 + 首任务引导 | 激活抓手：新用户首次对话预置高成功率模板（文件整理/周报生成），把首任务成功率拉到 ≥90%，缩短激活路径 | 主 SPEC §5.1 chat_submit 契约；§8.2 E2E「文件整理」场景 | 模板管理（平台侧）、引导流程（用户端） |
| G5 | 节省时间/成本月报 | 变现抓手：把抽象价值量化为「本月节省 12 小时、¥86」，是免费→付费转化的说服依据 | 无（全新） | 时长估算模型、月报生成与分享 |
| G6 | 定时任务自动化 | 留存抓手：定时周报/数据汇总等周期性任务把「周活跃天数」从 2–3 天拉升至 ≥4 天，任务自动运行不依赖用户想起产品 | 占位清单 ScheduleView（P1）；主 SPEC §3.4 tokio-cron-scheduler | 定时任务 command 族落地（占位清单已列缺失） |
| G7 | 邀请奖励 | 获客抓手：组织管理员邀请成员已存在，扩展为双向 token 奖励（各得 50 万 token 一次性额度） | 云端 spec §8 成员管理「邀请」 | 奖励发放经配额系统记账，防刷（设备/手机去重） |

抓手优先级排序：G4（激活）> G1（信任）> G2（生态）> G6（留存）> G3/G5（企业侧）> G7（获客）。理由：DAU 50K 目标下漏斗瓶颈在激活与留存，获客依赖产品口碑自然增长为主。

## 6. 数据指标体系（任务 2）

### 6.1 北极星指标

| 项 | 内容 |
|----|------|
| 指标 | 周有效完成任务数（Weekly Completed Tasks, WCT） |
| 定义 | 自然周内状态到达 done、且 24h 内无回滚、无用户差评的任务总数 |
| 计算口径 | `COUNT(tasks WHERE status='done' AND rollback_within_24h=false AND negative_rating=false)`，按周聚合；仅计平台托管 Key 与自备 Key 任务之和（双轨均计任务数，成本口径分开，见 §6.2 成本层） |
| 目标推导 | DAU 50K × 周均活跃 4 天 × 1.5 任务/活跃日 × 85% 成功率（主 SPEC §9.3）= 25.5 万 |
| 目标值 | ≥25 万/周（冷启动期 ≥2 万/周，增长期 ≥10 万/周） |

### 6.2 五层指标

**获客层**

| 指标 | 定义 | 计算口径 | 目标值 |
|------|------|----------|--------|
| 日新增注册用户数 | 当日完成注册的用户数 | `COUNT(users WHERE created_at IN 当日)`（云端 spec §4.2 users 表） | 冷启动 ≥200/日；稳态 ≥1,500/日（对冲月流失率 3%：50K×3%÷30≈50/日是下限，1,500 为增长型目标） |
| 注册→首登转化率 | 注册后 24h 内登录客户端的用户占比 | 首登用户 ÷ 注册用户 | ≥90% |
| 获客成本 CAC | 单个新注册用户的营销支出 | 营销总支出 ÷ 新注册用户数 | ≤¥20/人 |

**激活层**

| 指标 | 定义 | 计算口径 | 目标值 |
|------|------|----------|--------|
| 激活率 | 新用户注册后 24h 内完成 ≥1 个成功任务的占比 | 达标新用户 ÷ 新注册用户；成功=任务状态 done | ≥45%（冷启动 ≥35%） |
| 首任务成功率 | 用户第一个任务的成功率 | 首任务 done 用户 ÷ 提交过首任务用户 | ≥90%（高于总体 85%，靠模板任务 G4 保障） |
| 首任务交付时长 | 首次 chat_submit 到 Done 事件的中位耗时 | `MEDIAN(done_ts - submit_ts)`（主 SPEC §3.1.3 事件时间戳） | ≤10 分钟 |

**留存层**

| 指标 | 定义 | 计算口径 | 目标值 |
|------|------|----------|--------|
| 次日/7 日/30 日留存 | 第 N 日仍提交 ≥1 任务的用户占比 | 第 N 日活跃 ÷ 基准日新增 | ≥40% / ≥25% / ≥15% |
| 周均活跃天数 | 活跃用户周内有任务行为的天数 | `SUM(active_days)/COUNT(active_users)`，周窗口 | ≥4 天 |
| 核心用户占比 | 周任务 ≥5 的用户占 WAU 比例 | 周任务≥5 用户 ÷ WAU | ≥30% |

**变现层**

| 指标 | 定义 | 计算口径 | 目标值 |
|------|------|----------|--------|
| 免费→Pro 转化率 | free 组织升级 pro 的比例 | 升级组织 ÷ 存量 free 组织（云端 spec §4.2 plan 字段） | 上线 12 个月 ≥5% |
| 付费组织数 | plan∈{pro, enterprise} 的组织数 | `COUNT(organizations WHERE plan!='free')` | 12 个月 ≥200 |
| 组织月均收入 ARPPU | 付费组织平均月付费 | 月收入 ÷ 付费组织数 | ≥¥2,000/月 |
| 净收入留存 NRR | 存量付费组织本期收入 ÷ 上期收入 | 含扩容、降级、流失 | ≥110% |

**成本层**

| 指标 | 定义 | 计算口径 | 目标值 |
|------|------|----------|--------|
| 单任务平台 token 成本 | 平台托管 Key 承担的单任务成本 | 平台 token 支出 ÷ 任务总数（仅计走 Gateway 的调用，云端 spec §2） | ≤¥0.15/任务 |
| 单 DAU 日成本 | 平台日成本 ÷ DAU | (token 成本+Runner 基础设施) ÷ DAU | ≤¥0.20（¥30 万/月 ÷30÷50K） |
| 降级调用占比 | 因配额/限流切至低成本模型的调用占比 | 降级调用 ÷ 总模型调用 | ≤15%（超过说明配额或预算设置过紧） |
| 自带 Key 用户占比 | 使用自备模型 Key 完成任务的用户比例 | 自备 Key 任务用户 ÷ 活跃用户（主 SPEC §10.3 双轨） | ≥30%（成本对冲） |
| 毛利率 | (收入−token 成本−基础设施成本) ÷ 收入 | 月度口径 | ≥60% |

## 7. 增长策略：分阶段路径（任务 3）

| 阶段 | 目标 | 关键动作 | 衡量标准 |
|------|------|----------|----------|
| 冷启动（第 1–2 月，0→5K DAU） | 验证激活闭环 | ① 种子用户 1,000 人定向邀请（桌面端存量用户优先，local-first 用户转云端）；② 模板任务库上线（G4），首任务强制走引导；③ 免费配额放宽至 50 万 token/日（限冷启动期）；④ 每周复盘激活漏斗，48h 内修复卡点 | 激活率 ≥35%；次日留存 ≥30%；首任务成功率 ≥85%；崩溃率 <0.3%（主 SPEC §9.3） |

## 8. token 预算管控机制设计需求（任务 4）

### 8.1 与现有设计的对齐与增量

| 项 | 现有设计 | 本报告增量 |
|----|----------|-----------|
| 计量点 | Gateway 统一计量平台托管 Key（云端 spec §2） | 保持 Gateway 为唯一计量点；增加任务/agent 维度标签，使计量记录可下钻 |
| 配额维度 | 组织级 QuotaPlan（云端 spec §4.2 organizations.plan）+ 按成员/工作区聚合（§8） | 新增用户级、agent 级、任务级三层配额；工作区聚合语义并入 agent 维度 |
| 超限动作 | 排队降级（云端 spec §10.2 Runner 风险缓解）；429 指数退避（主 SPEC §3.2.4：1s→2s→4s→8s 最多 4 次） | 明确三级动作顺序与触发阈值；新增「预算熔断」，与主 SPEC §3.2.4 的可用性熔断（P95>8s、错误率>15%/5min）并列且互不替代 |
| 告警 | 「配额阈值告警」（云端 spec §8，未定义阈值） | 量化为 70/85/95/100% 四档 |

### 8.2 配额维度与默认值

| 维度 | 默认配额 | 硬上限 | 说明 |
|------|----------|--------|------|
| 平台级（预算） | ¥1.2 万/日软顶，¥30 万/月硬顶 | 月硬顶不可在线突破 | 超日软顶触发全局模型降级；超月硬顶阻断全部免费层平台调用 |
| 组织级 | free：200 万 token/月；pro：3,000 万/月；enterprise：合同自定义（起售 1 亿/月） | enterprise 上限 10 亿/月 | 对齐云端 spec §4.2 plan 三档 |
| 用户级 | free：20 万 token/日 且 400 万/月；pro：100 万/日 且 2,400 万/月 | 日配额 ≤ 组织月配额 ÷10 | 防单用户耗尽组织额度 |
| agent 级 | 单 agent 单日消耗 ≤ 所属组织日配额的 30% | 50% | 防单个失控 agent（循环重试）拖垮组织预算；对齐云端 spec §10.2 Runner 成本风险 |
| 任务级 | 软上限 6 万 token，硬上限 10 万 token | 20 万（需管理员放行） | 超软限在任务内提示并建议降级模型；超硬限任务暂停并等待用户确认（复用主 SPEC §3.1 状态机 paused 语义） |

并发侧约束沿用主 SPEC §3.5.5（每工作区并发模型调用默认 3/硬限 5，任务队列默认 100/硬限 500），峰值并发会话 2000 作为 Gateway 全局限流上限的容量基线。

### 8.3 预警阈值与超限动作

| 阈值（占配额周期用量） | 动作 |
|:--:|------|
| 70% | 用户端站内提示 + 组织 admin 收到通知（信息级） |
| 85% | 告警级：新任务自动降级至低成本模型；admin 收到邮件/站内信；控制台看板标黄 |
| 95% | 严重级：新任务进入排队队列（FIFO，队列深度沿用主 SPEC §3.5.5 默认 100/硬限 500）；运行中任务完成后冻结；看板标红 |
| 100% | 阻断级：拒绝新任务，返回错误码（扩展主 SPEC §5.3 错误体系，新增 QUOTA_EXCEEDED），前端引导升级或等待下一周期 |

超限动作优先级固定为：**降级模型 → 排队 → 阻断**。降级链复用主 SPEC §3.2.3 Router 降级链与 §3.2.4 熔断表；429 外部限流沿用指数退避（1s→8s，最多 4 次）。预算熔断（全局日成本达预算 95%）独立于可用性熔断，触发动作是全局降级而非切换备用模型。

### 8.4 成本看板需求（管理控制台）

1. **预算水位**：平台/组织两级日、月预算使用率实时条（阈值色标对齐 §8.3 四档）；
2. **多维下钻**：token 消耗与费用按 组织→成员→agent→任务 四级下钻（扩展现有云端 spec §8「按成员/工作区聚合」，新增 agent 与任务级）；
3. **趋势与预测**：7/30 日消耗趋势线 + 按当前速率的本月预测值；
4. **双轨分离**：平台托管 Key 成本与自备 Key 调用量分列展示（对齐主 SPEC §10.3，避免口径混淆，R6）；
5. **降级/阻断事件流**：展示每次降级、排队、阻断事件与受影响任务数；
6. **导出**：CSV 导出（对齐云端 spec §8 审计检索导出能力）。
