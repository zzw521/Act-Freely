## 3. 状态明细（给要接手的窗口：实际形状）

### 3.1 `prepare_fn` 从注入位变成真件

新增 `engine/ticket_workspace_prepare.py`（429 行，纯标准库）。D-48.1 起 `TicketWorkspace.prepare`
就留着 `prepare_fn` 这个注入位，注释写着「典型是 git worktree，由调用方注入」——但到今天
**没有任何真实装配注入过它**（`ticket_worker_service` 传的是 `None`），所以执行体拿到的永远是一个
空目录。现在三种规格都是真件：

| 规格 | 实际动作 | 拒绝什么 |
| --- | --- | --- |
| `{"kind":"repo","repo":"D:/x/y","ref":"main"?}` | `git -C <源仓> rev-parse --git-dir` 探仓 → `git worktree add --detach [ref] <目标>` | 源仓不是仓（回 `rc`）、换来源复用同一目录 |
| `{"kind":"url","url":"…","ref"?,"depth"?}` | `git clone --depth N [--branch ref] -- <url> <目标>` | `depth` 非正整数（**`0` 不再被静默当成 1**） |
| `{"kind":"command","argv":[…]}` | 直接 `exec`，**不经 shell** | 字符串 argv；含 `& \| ; < > $ \n \r` 的元素 |

接口面（别的窗口要接就照这个形状）：

- `normalize_spec(spec) -> dict` / `build_preparer(spec, **kw) -> (WorkspacePreparer | None, 中文理由)`
  —— **建不出来不抛异常**，抛出来的话会让整个工单服务起不来。
- `WorkspacePreparer.__call__(path)`（就是 `prepare_fn`）、`.fingerprint`（sha256[:12]，覆盖规格
  **去掉 `timeoutSeconds`**）、`.cleanup(path)`、`.describe()`（**不含任何凭据**）。
- `remove_created_tree(path, root=…)`：只在 worker 根之下动手，删的是**本次自己创建**的目录。
- 超时缺省 600 秒、夹在 `[1, 3600]`；一律注入 `GIT_TERMINAL_PROMPT=0` 与**强制赋值**的
  `GIT_ASKPASS=""`（`setdefault` 挡不住外层环境里已经存在的那个会弹窗的 askpass）。
- 失败理由先按凭据形状打掉再出门：`user:token@host`→`user:***@`、
  `--password/--token/--api-key=`→`***`。这条不是洁癖——失败理由会进模型回话与状态面。

三条只有跑起来才看得见的口径，各带用例：

1. **换来源拒、来源未知放行，但放行 ≠ 重跑**。标记文件 `.ticket-worker.json` 里存
   `prepareFingerprint`；legacy / 坏标记判成「来源未知」照旧用已有目录，但**一次外部动作也不多来**
   （用例钉的是 `preparer.calls == 0`）。
2. **失败清理的顺序是先删目录、后 `git worktree prune`**。这是探针打出来的，不是推理出来的：
   `worktree add` 登记过之后再删目录，源仓留下「missing but already registered worktree」，
   同一路径第二次准备**必然**再撞 `rc=128`。倒序的反证也真跑了一遍。
3. **规格的来源只有两处**：进程内 `configure(prepare=…)` / `apply_prepare`，与环境变量
   `TT_TICKET_WORKER_PREPARE`。写面端点 `/api/tickets/config`、`/api/tickets/wakes` 见到
   `prepare` / `prepareSpec` / `prepareFn` / `workspacePrepare` / `worktree` **任一键就 400 并说明
   为什么**——不是静默忽略，静默忽略让调用方以为配上了。

状态面（`TicketServiceRuntime.prepare_state()`，已挂在 `/api/tickets/status` 的 `prepare` 段）：
`{enabled, kind, label, fingerprint, timeoutSeconds, source, reason?, note?}`。没配规格是**正常状态**
不是故障（空目录就是可运行的最小工单工作区），所以除 `enabled` 还回一句 `note` 告诉人从哪里开；
换规格失败时**旧的那份不动**；已经在跑的工单不会被换掉目录（目录已存在 `prepare()` 直接返回）。

### 3.2 按剩余窗口取页

算术只有一份，在 `engine/ticket_worker_adapter.py`：

- `window_budget(window, *, default, maximum, unit_tokens, what, floor=None) -> (default', max', 中文说明)`
  —— **只压不抬**；留 `WINDOW_RESERVE_FRACTION = 0.25` 余量；**永不清零**；
  **没有窗口信息时原样还固定预算并回空说明**（今天所有装配都没配 `contextWindow`，这里回一句
  「按窗口收窄了」页面就在说谎）。
- 下限**按页自己的单位**：正文 `WINDOW_PAGE_FLOOR_UNITS = 200`（字符）、
  列表 `WINDOW_PAGE_FLOOR_ITEMS = 3`（条）。
- `ReadWindowMeter`：**先建后填**。窗口要等策略归一化算完（故障转移链取最小窗口那条）、用量要等
  第一次模型回报；装配期快照在换模型配置那一刻就过期，所以工具面读的是现值。
  `reading()` 在窗口为 0 时回空字典 → 走完全没变过的固定预算老路。
- 列表的单条成本用 `list_unit_tokens(这一页真实条目)` 折算，不是「每条大约 N token」那种编造值。

接线到的两面（**第三面没做，见 §4**）：

- worker 执行体：`TicketToolbox.window_provider`，且 `TicketServiceRuntime` 构造里为
  **注入式 toolbox** 补接（`if self.toolbox.window_provider is None: set_window_provider(...)`）——
  不在构造参数里接，最像真机的那条路反而不生效。
- 引擎主会话：`server.py` 三个读取件都走 `_window_reading()`（正文两件内联传参，列表先取成变量再喂
  `window_budget`），`read_window.configure(policy.context_window, policy.context_window_from_model)`
  在装配时挂上，用量回调包一层 `_usage_capture_for_window(on_usage, read_window)` **先记账再转发**。
- 没给 `extra={"read_window": …}` 的装配点（含所有既有自测）**逐字等于改造前**，页面里也不出现
  一句关于窗口的话。

### 3.3 本刀抓出并改掉三个真缺陷

1. **列表的下限被正文的下限冒充**。`window_budget` 的缺省下限是 200「单元」，列表复用同一函数时
   `min(200, 50) = 50 ≥ default 20` —— 于是**窗口再紧也算不出变化**，列表那一面此前从来没被压小过。
   修法：下限做成参数，`budgeted_list` 与 `server.py` 的列表都传 `WINDOW_PAGE_FLOOR_ITEMS`。
2. **`depth: 0` 被静默当成 1**（git 的浅克隆没有「0 层」这种写法）。现按显式给值判存在性，
   非正整数直接拒并说清该怎么写。
3. **通道里台账那份与取页那份是同一个字典**，本地字符估算会流进真实用量台账。现拆成
   `ledger_record`（只拿上游回报）与取页读数（回报缺失才用估算，且页面里写明「这是折算值，
   不是厂商 tokenizer 计数」）——**假用量绝不进真实台账**这条口径自此有机器钉子。

另有一条**不是缺陷但值得记**：`engine/ticket_turn_scheduler.py` 的 `_start_job` 重建结果字典会把
`prepareFingerprint` 掉出去。那个文件**不在本窗口名下**（mtime 11-03 11:08），没去改它，改成在服务层
`submit()` 里按 `delivered == "started"` 现算指纹——效果等价且不动别人的文件。

- **真实私有仓 + 真实 IM 的端到端未跑**。本机 git 是真件、worktree 是真建出来的（`.git` 是文件不是
  目录、源仓登记里看得见这一份、换 ref 判换来源并拒），但「工单在 worktree 上干活并把结果回给用户」
  这条链没在真机点过。
- **界面还没有准备规格的开关**。目前只有进程内 `configure(prepare=…)` 与环境变量两个口；桌面壳要把
  这一位推给引擎（与 `writeStaging`、模型档位同一份 runtime 载荷，见更新卅六⑤对 137-④ 的裁决），
  还需要「待准备的工作区」在界面上怎么呈现。**这是桌面半边的缺口，不是引擎的。**
- **窗口取页在真实模型下的手感未验**。`TOKENS_TO_UNITS = 2` 是保守折算，页面文案从不声称精确；
  真实 tokenizer 下压得偏多还是偏少，要等 #162 那批真模型验收（需要 Key，只走环境变量）。
- **`GIT_TERMINAL_PROMPT=0` 只管 git**：`command` 类规格跑的是任意 argv，命令自己要口令就会挂到超时；
  超时到点**先 kill 再收目录**，但这条只在服务层有用例，没在真机验过挂口令的命令。
