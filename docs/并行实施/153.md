> **D-27 服务端半边（W1 #153）**：哈希链从来只能证明「行与行相连」——同时握着库文件和源码的本机用户删掉一行、再从创世哈希把整条链重算一遍，逐行验链会全盘通过，这是旧 `verify` 的结构性盲区。本轮补的是**签名锚点**：把 `(fromId, toId, entries, headHash)` 用服务端 RS256 私钥签掉（`aud=tongtian-audit`、`typ=audit-anchor`，摘要 `digest = sha256(canonical(fields))`，公钥走既有 `/.well-known/jwks.json`），锚点行落在新表 `audit_anchors`；改了正文 ⇒ 链头对不上，删了行 ⇒ 条目数与首行号对不上，**重算了整条链 ⇒ 与更早的锚点对不上**——这一层是逐行判定永远给不出的。锚点签发前置三道拒签：链有断点 `409 AUDIT_CHAIN_BROKEN`（点名行号与中文原因）、超过单次巡检上限 `507 AUDIT_TOO_LARGE`、空链 `409 AUDIT_EMPTY`，**不给已断裂的链条盖可信章**。旧 `verify()` 改名并加宽成 `verify_report()`（新增 `firstId/lastId/contiguous/breakCount/scanLimit/truncated` 六字段，保留原有 `entries/headHash/brokenAt/breaks/legacyRows/ok`），另加 `verify_prefix()` 按锚点重放前缀；`GET /api/v1/admin/audit/verify` 的响应自此变宽，既有消费者（含 `tongtian-gateway/scripts/m4_acceptance.py:735` 只断言 `ok is True and brokenAt is None`）不受影响。**远端归档是可选的且三处不谎报**：未配 `TT_AUDIT_ARCHIVE_URL` 时 `pushed=false` 并直说「只出本地锚点，不算已归档」；锚点覆盖行数超过单次推送上限 2000 时**标 `skipped` 并拒推**——只推半条链会让对端算不出链头，那比不推更像造假；推送失败把原因写进行里（`archive_state='failed'` + `archive_error`）**并在事务提交之后**才转 502，因为 `tx()` 内抛异常会把这条「推过但没成」的证据一起回滚掉。归档地址必须 HTTPS（本机回环允许 HTTP），与登录回调同一条口径。**合规报告** `GET /api/v1/admin/audit/compliance`（契约版本 `audit-compliance.v1`）把 11 类结论码分 error/warn 摆明（`SCAN_TRUNCATED / LEGACY_ROWS / ID_GAP / CHAIN_BREAK / NO_ANCHOR / ANCHOR_MISMATCH / ANCHORS_NOT_FULLY_CHECKED / NO_REMOTE_ARCHIVE / NOT_ARCHIVED / ARCHIVE_FAILED_ROWS / ARCHIVE_SKIPPED`），`verdict.trustworthy` **只在「链自洽 ∧ 有锚点 ∧ 锚点全部可信」三者同时成立时为真**，`coverage.notCovered` 如实写出这份报告证明不了什么（引擎与桌面本地审计不在这条链上、载荷脱敏与 4KB 截断、用量保留期）；`…/compliance/export` 出 Markdown 六板块，末节标题就是「六、本报告证明不了什么」，响应头带 `X-TT-Audit-Head` 与 `X-TT-Audit-Trustworthy`。签发与归档走新的 `require_anchor_writer`（管理员 / 网关运维），审计员保留全部读权——**审计员能出报告、能验锚点，但不能造锚点**，否则「谁都能盖章」与「盖章有意义」冲突。

## 4. 仍未做（不许被读成已做）

- **真实远端归档对端未验收**：自测跑的是本机 `ThreadingHTTPServer` 假 sink——它独立用 JWKS 公钥验签、核 `aud/typ/四字段/digest`，但它是我们自己写的。**任何真实 WORM / 存证服务的接入、TLS 证书链、重试与幂等语义全部未验**。
- **控制面界面零**：`app/web/**`（W1 领地）里没有锚点签发按钮、没有合规报告页、没有归档状态看板。今天审计员只能用 curl。**这是本项「合规报告」验收的真正缺口**，不是可选项。
- **没有自动/例行签发**：锚点靠人工 `POST …/anchor`。「篡改必须发生在最近一次锚点之后才抓得住」这条纪律目前只有代码注释与本报告，没有定时器、没有部署钩子。
- **锚点只向前作证**：删行/改行发生在最新锚点之后时，最新锚点仍判可信。合规报告用 `ID_GAP`（error）与 `NO_ANCHOR`（warn）如实点名，但**不阻断签发**——这是设计边界，读状态时不要读成「任何篡改都会立刻被抓」。
- **同机私钥这条根本边界没变**：同时持有数据库文件与签名私钥的人可以连锚点一起重造，本地无任何手段能证明他没有。唯一能破的是远端归档；未配置时报告给 `NO_REMOTE_ARCHIVE` warn 并写明「同时持有库文件与私钥的人可以连锚点一起重造」。
- **密钥轮换**：`KeyStore.MAX_KEYS = 2` ⇒ 轮换两次以上的旧锚点验签失败（`签名密钥不在 JWKS 中`），本刀没有实现「轮换后自动重签全部锚点」。**与 D-44 分片里那条是同一个边界，建议合并成一张「轮换后重签」工单。**
- **三个硬上限没有分片方案**：单次巡检 20000 行（超出 ⇒ `SCAN_TRUNCATED` error 且拒签锚点）、单次推送 2000 行（超出 ⇒ `skipped`）、单次比对 200 个锚点（超出 ⇒ `ANCHORS_NOT_FULLY_CHECKED` warn）。链长过这些数就需要分段锚点/分页归档，本刀没做，也**没有大链实测**（自测最大约几十行）。
- **多实例与备份恢复**：`seq` 自增、链与锚点同库，容器重启/备份回滚后的锚点连续性未验；两个服务实例共享一份 SQLite 的场景未验。
- **下载面只在 HTTP 层断言**：`Content-Disposition` 文件名与 CRLF 转义、Markdown 表格里的竖线转义有单测，但没有用真实浏览器点过一次「导出」。
- **本仓库没有 pytest**：服务端自测族是 stdlib 脚本，判定看 `^  ✓` 计数与末行「通过 N 项」；本卡的 94 项全部来自 `tests/test_audit_anchor.py` 实跑日志（`docs/并行实施/_w1-logs/153-anchor.log`）。
