## 2. 口径句（供「更新N」条目使用，编号由 W4 合并时定）

> **① 落地（D-18 引擎侧注入面半边，本批次 W7 #155）**：`engine/runtime_context.py` 组装段
> 新增四个总量常量——套件/SKILL 描述逐件截到 **300 字**（`MAX_SKILL_DESC_CHARS`）、
> 意识四段合计 **12,000 字**（`MAX_AWARENESS_TOTAL_CHARS`）、附件合计 **48,000 字**
> （`MAX_ATTACH_TOTAL_CHARS`）、剩量不足 **300 字**的那段整段不塞（`MIN_SECTION_FIT_CHARS`），
> 统一走新增的 `_budget_sections`。**铁律照旧：截了或没塞进去必须留下一句用户看得见的说明**，
> 说明随 `context_notes` 走 SSE 步骤事件，不静默丢内容。基准侧配套：
> `tests/integration/engine_long_task_bench.py` 加了注入负载档（`BENCH_INJECTION=typical|heavy|none`）
> 与 A/B 开关（`BENCH_CAPS=off` 把四个常量在基准侧推到不生效，复现「只有单件上限、没有总量上限」
> 的改动前形状；生产代码里没有留开关），并把 D-18 三指标算进 `ENGINE_BENCH_JSON.efficiency`。
> **同机两档两侧实测（约束 A，全部落在报告 §8）**：heavy 档每任务折算 tokens
> **1,796,183 → 856,660（−52.3 %）**、重复注入占比 **0.9067 → 0.8455**、
> 每千 tokens 墙钟 **0.840 → 1.994 ms**（**这个指标会反向，见下**）；
> typical 档每任务 tokens **650,481 → 649,048（−0.2 %）**、占比 **0.8226 → 0.8233**、
> 每千 tokens 墙钟 **3.478 → 3.640 ms**。
> **挖出来的真缺陷是压缩空转**：改动前 heavy 档 104 次任务调用配了 **103 次摘要调用**——
> 固定注入本身就把单次请求顶到折算峰值 38,055（窗口配的 32,768），每轮触发压缩、
> 每轮只换回一点余量（注入部分压不掉）、下一轮又超；上限生效后摘要调用降到 **21 次**，
> 请求体总量 28.74 MB → 13.71 MB。**两条必须一起写的读数纪律**：
> (1) `wallMsPerKToken` 的分子是链路自己的开销（已减掉假端点每次自己 sleep 的 40＋25 ms），
> 它按**调用次数**走、不按体量走，注入变少时该比值**上升**而绝对墙钟与 tokens 同时下降，
> 只能和 `wallMsPerTask`/`engineOverheadMsPerCall`/`measuredCalls` 同读——这条已写进
> 基准 JSON 的 `caliber.efficiency`，防止下一个人拿它当「越小越好」报退步；
> (2) 本刀新加了重复字节分列 `repeatInjectionBytesSystem` / `...History`，实测改动前
> heavy 档 26.06 MB 重复字节里 **93 % 是每轮原样重发的 system 注入段**，改动后仍占 73 %
> ——**总量上限只能把注入段变小，不能让它只发一次**，残留的大头还在注入段本身，
> 不在「历史携带」上。同配置复跑（heavy＋caps on 连跑两次）墙钟 18,199 → 14,959 ms（−17.8 %），
> 而 tokens、字节、占比、摘要调用数**一字不差**——所以台账引用按「计数量是确定值、
> 毫秒按量级＋噪声读」，七窗口同机并行时别拿单个毫秒数下结论。

## 4. 未验收与边界

- **Rust harness 侧的注入面没有同步瘦身**。`src-tauri/src/harness/prompt.rs` 只有
  `MAX_AWARENESS_FILE_CHARS=6000` / `MAX_MEMORY_FREEFORM_CHARS=3000` / `MAX_SKILL_LIST_ITEMS=40`
  这类**单件/单数**上限，**没有意识各段的合计上限**，`skills_prompt` 把 `s.description`
  **逐字下发**（无长度截断）。⇒ 本报告 §8 的收益只属于 Python 链路。镜像请求见 §5。
- **真实模型、真实分词、真实单价、真实网络**一个都没碰；全部是假端点的字节 ÷ 4 折算口径。
  「压缩空转」那 82 次多余调用在真端点上是**真金白银**，但具体数额不能从本表推。
- **首包时延没有对照**：D-18 验收里「首包时延有可量化下降」这一半**本刀没有数据**，
  四跑只报了 tokens/字节/占比/调用次数/墙钟。要补就在 `BENCH_CAPS` 两侧各加一组
  `first_packet_ms` 对照，本刀没做。
- **产物质量只做到「没变少」**：四跑都断言 `files_written ≥ 100`、
  「压缩真的取到了结构化摘要」，没有做人工评审比对截断前后模型输出质量。
  「不牺牲产物质量」这条验收**不能算已验**。
- **残留重复的大头仍在携带方式**。改动后 heavy 档 11.59 MB 重复字节里 8.42 MB 还是每轮重发的
  system 段。要再降得动主会话携带（同一份注入只首轮全文、后续带引用，或吃上游 prompt cache），
  那部分在 `engine/server.py` 与 `context_budget` 的领地，**不在卡 #155 领地，W7 一行未碰**。
  这是**建议的下一刀**，不是本刀的遗漏。
- §8.4 第 3 条那句因果（改动前显得「历史干净」是因为每轮把历史折进了摘要）是**从计数量推出来的
  解释**（依据＝携带消息数 8 vs 12、摘要调用 103 vs 21），没有单独做隔离实验去证。
