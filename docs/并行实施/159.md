### 3.2 盘上布局（全在数据根下 `update/`，数据根只经 `security::file_perm::data_root()` 取）

```
<数据根>/update/
  channel.json               渠道：{channel, url, enabled}；空串 url = 清除渠道，「关掉但留着地址」由 enabled 表达
  trusted_publishers.json    本机信任：只存 {publisherId, publicKey}；指纹与来源每次读盘重算
  journal.json               状态机 + staged + pending + rollback（回滚材料）
  ledger.jsonl               动作留痕，上限 500 行、写时截断
  staging/<name>.part        下载中
  staging/renwoxing-<platform>-<arch>-<version>-<sha256前12位>-<kind>.<ext>   已核验的暂存包，最多留 3 份
```

文件名里那 12 位哈希是**自己编的标记**，所以 `find_package_for_version()` 找到候选后会读回来重算一次 sha256：账本里有记录就比完整哈希，没记录时只能要求完整哈希以那 12 位开头——这是文件名与内容之间唯一可用的绑定，回滚材料因此是**按内容认**的，不是按名字认的。

### 3.3 15 个方法与请求字段（`lane_exec` 分派，`payload` 都是对象）

| method | 请求字段 | 说明 |
| --- | --- | --- |
| `update_describe` | — | 自述：方法清单、常量表（大小上下限/上限条数/确认词/状态集）、样例清单 JSON |
| `update_channel_get` | — | 只读，带 `loadNote` |
| `update_channel_set` | `url` `channel?` `enabled?` | 唯一的写入闸门：URL 不合法整条拒（不落盘半成品） |
| `update_trust_list` | — | 内嵌 + 本机，带 `embeddedCount` |
| `update_trust_add` | `publisherId` `publicKey` | 只增；同标识不同钥 → `UPDATE_PUBLISHER_KEY_CONFLICT`；上限 50 |
| `update_trust_remove` | `publisherId` | 内嵌锚点删不掉（如实拒绝） |
| `update_check` | — | 取清单 + 判定，**不写盘**；一次动作只取一次清单 |
| `update_download` | `version` | 不给版本号就拒；不默认下「最新那条」 |
| `update_status` | — | 先结算再回报；状态不认识时给 `stateKnown:false` |
| `update_install_plan` | `file` `version` | 只生成命令，不动手 |
| `update_install` | `file` `version` `confirm` | 确认词 `UPDATE` 才 spawn |
| `update_rollback_plan` | — | 只读：有没有回滚材料、命令长什么样 |
| `update_rollback` | `confirm` | 同一个确认词；`pending` 未结算时拒绝连发第二次 |
| `update_import_local` | `path` `version` `confirm` | 确认词 `LOCAL-PACKAGE`，来源标 `local-import` |
| `update_ledger` | `limit?` | 回报 `totalLines / truncated / badLines` |

**两类失败要分清**：业务性拒绝回 `ok:false + reason`（中文，说清停在哪一步、下一步该干什么），**不进车道的错误账本**；只有 `Err` 才记进 `ledger.jsonl` 并被 `error-messages.ts` 的码表接住。界面接的时候按这个分叉渲染，不要把「本机没有回滚材料」画成崩溃。

### 3.4 清单与签名（`tt-app-update/1`）

- 顶层：`schema / channel / publishedAtMs / revokedVersions[] / releases[]`；release 有 `version / minAppVersion? / notes? / artifacts[]`；artifact 有 `platform / arch / kind / url / sha256 / sizeBytes / publisherId / signature`。
- `deny_unknown_fields`：**写了宽松档的清单会被当格式错误整条拒掉**，而不是被读成一个我们其实没实现的开关。上限：200 个 release、每条 12 个产物、200 条撤销、notes 4000 字、URL 2048 字、包 1 KiB–2 GiB。
- 签名载荷是七行拼接：`tt-app-update-v1 \n 渠道 \n 版本 \n 平台 \n 架构 \n 类型 \n 发布者 \n sha256`；市场域 `tt-market-v1` 的签名拿来当更新签用**必须验不过**（自测真造一把钥、真跨域签了一次，见 `manifest.rs` 的 `test_*`）。
- `revokedVersions` 除了拦对应版本，还会在本机当前版本被撤销时给出 notice（「建议尽快更新」），`minAppVersion` 参与可装判定。

### 3.5 状态机与结算

`empty → staged → install-pending → installed | rolled-back | install-failed`（`STATES` 六个值；自测扫**生产段**（`#[cfg(test)]` 之前）断言源码里没有 `journal.state = "字面量"`，状态只能通过常量写进账本——这条一开始写成扫全文，被自己的测试字符串踩了一次，改成扫生产段才是真判据）。

结算只看一件事：`CARGO_PKG_VERSION` 变没变。三个结局分开写，其中「版本变了但不是清单说的那个」如实报成装错了包，不替用户解释。判定做成 `settle_with(paths, installed)` 是因为版本号是编译期常量：**做成参数才谈得上在测试里演两条分支**，而不是去改环境变量（跨模块共享会互相打架）。`ENGINE_VERSION` 与它不是一回事，绝不参与比较。

**应用不自动退出**：`quit_note` 与 `note` 都写清「安装器不会替你先退出应用，正在运行的程序会让覆盖失败」。这条是刻意的——程序自己 kill 自己再装，失败时连看的人都没有。

### 3.6 URL 口径（这是 SSRF 面，不能靠「看着像 https」放行）

远程只许 HTTPS；主机名解析后每个地址都必须是公网（私网 / 回环 / 链路本地 / 广播 / 文档段 / `0.0.0.0` / CGNAT `100.64/10` / `198.18/15` / `240/4` 全拒，v6 含映射 v4 与 ULA）；**回环例外只许 HTTP，给自建与联调源用**；拒绝 URL 内嵌用户名密码；**`.redirect(Policy::none())`**，3xx 不当成功。

## 4. 未验收与边界

1. **设置页一行未接**：渠道输入、信任公钥管理、「可更新 vX」的按钮都没有。`tests/unit/security/dead-controls-realized.test.ts` 钉着「不得出现『检查更新』假按钮」，所以本卡不动 UI；接的时候只需在 `contracts_exec.ts` 已声明的通道上走 `laneDispatchOf`，**不必打开 `contracts.ts` 或 `lib.rs`**。
2. **没有发布端**：服务端不产这种清单、没有发布私钥与签名流程。钥匙出现之前，`EMBEDDED_ANCHORS` 保持为空是正确状态；加了钥那天这里加的必须是**公钥**，私钥只在发布机。
3. **灰度没做**：schema v1 里有意没有百分比/分组字段。要做得先解决一对矛盾：清单「未知字段一律拒」保护的是旧客户端不被新语义绕过，而灰度字段天然只有新客户端读得懂——真要加，先想清楚旧版本读到它时应该装还是不装。
4. **真机一次也没装过**：NSIS `/S`、MSI `msiexec /i /quiet /norestart`、UAC 被拒、文件被占用四条分支只有代码与自测。`install-failed` 那条的文案是推测性归因（「多半是没退出应用」），真机跑之前不许当成诊断结论。
5. **非 Windows 只验到「拒得干净」**：`install_plan()` 在非 Windows 直接 `UPDATE_UNSUPPORTED_ARTIFACT`；macOS / Linux 的安装器路径未实现（清单词表已经接受这两个平台，所以补实现不必改 schema）。
6. **统一审计没接**：`ledger.jsonl` 是本车道自己的留痕，`update_ledger` 的 `note` 里就写着这句；D-26（审计）落地后应当并过去，不要出现两套「谁在什么时候动了什么」。
7. **`reqwest` 没有 `blocking` 特性**：所以车道分派是 `async`，测试里用 `tokio::test` + `block_on`；接界面时不要以为能在同步上下文里调。

## 5. 跨语言契约（13 项，`tests/unit/shared/app-update-contract.test.ts`）

本仓库没有 git，Rust 改了 TS 不知道是 D-12 以前的老故障面，所以四处命名互相钉死：

- TS `IPC_CHANNELS_EXEC` 里的 `update_*` 通道 ↔ Rust `METHODS` ↔ `dispatch_in` 里 `"{m}" =>` 分支 ↔ `ipc/exec.rs` 的 `pub const LANE: &str = "exec"`；
- 五个视图函数（`staged_row` / `retained_row` / `anchor_view` / `artifact_view` / `channel_view`）实际 `json!` 的键集 ↔ 对应 TS interface 的字段名，**双向**；
- `STATES` ↔ `UpdateState` 联合成员；`ACTION_*` ↔ `UpdateAction`；
- `UPDATE_*` 码：Rust 源码里抛的必须进 `error-messages.ts`，登记表里挂的必须有人在抛（两个方向都查）；
- 防空跑：`jsonKeysOf` 与 `tsFieldsOf` 都断言解析出的条数 `> 3`，`emitted.size > 8`。这三条不是洁癖——同一族断言曾经因为解析正则写错而「绿着什么都没比」，本卡把它钉成可见的失败。
