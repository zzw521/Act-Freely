## 2. 口径句（供「更新N」条目使用，编号由 W4 合并时定）

> **① 落地（D-11 引擎可离线半边，本批次 W7 #160）**：新建四件
> `engine/audio_adapters.py` / `audio_asr_runtime.py` / `audio_tts_runtime.py` / `audio_barge_in.py`，
> 全部**只用标准库**（`urllib`/`base64`/`json`/`uuid`/`re`），**零依赖新增**。
> 形状是「可插拔适配器 + 注入 transport」：`AudioAdapter(uploads_audio, implemented)` 两个位决定一切——
> **`uploads_audio` 是隐私门的唯一判据**，`implemented=False` 的通道（系统识别、whisper.cpp）
> 在选型阶段就排除出「要上传音频」的候选，所以真机没接上时**不会被静默当成可用**；
> transport 由调用方注入，自测**永不联网**。配置优先级
> `runtime.audio.<kind>` > `TT_ASR_*` / `TT_TTS_*` > 模型配置（缺省 `whisper-1` / `tts-1` / `alloy`），
> 只配地址或只配密钥都**如实点名缺哪一项**、给出可填位置，且说明里不回显任何已配好的值。
> ASR 走 OpenAI 兼容 `/audio/transcriptions`（multipart 只用标准库拼；`None` 的语言码**整条不出现**
> 而不是写成字符串 "None"——上游会把那种值当合法语言码收下去再报一句没人看得懂的错），
> 结果成功才给 `text` + `insert:{text, position:"cursor"}`，失败只给 `error` 原因，
> **不用空串冒充「识别到空白」**；只对 429/5xx 与「连不上」重试一次，超长转写截到 8,000 字并留说明。
> TTS 走 `/audio/speech`，朗读前先剥排版（代码块 / 表格 / 图片 / 链接地址 / URL / 行内代码 / HTML /
> 标题 / 项目符号 / 强调各留一条自己的说明），再按句末边界分段（没逗号时**不切半句**），
> 单轮最多 12 段，**任一段失败就点名是第几段失败并保留前面已合成可播的段**。
> 打断是**独立状态机**（6 状态 / 12 事件），所有时间戳由调用方注入 `now_ms`
> （本层不调 `time.monotonic`——vendor 的解释器粒度是 15.6 ms，判不了 280 ms 的打断下限）；
> 判定顺序是回声守卫 → 附和词 → 停词 → 状态 → 已停止 → 时长 → 能量，**反过来写会让「停」被时长条件误伤**；
> 状态只有一个落地点（`_record`：转移、动作、日志行同批写），杜绝「状态改了日志没记」。
> 契约测试 `tests/integration/engine_audio_selftest.py` **198 项**（`^[PASS]` 判定，零红），
> 假上游逐条记录 method/URL/头/体/超时，专门断言**密钥只进请求头、绝不进请求体或错误文案**
> （`sanitize_error` 先掩成 `***` 再截 300 字）。

## 3. 状态明细（D-11 一节下新增）

**状态**：**引擎可离线半边已落地（2026-11-04，W7 #160）**——适配器登记与选型、隐私门、
上游地址解析、载荷校验、ASR/TTS 请求构造与失败原因、朗读文本分段、打断状态机与接回计划
都有自测钉住；**整项仍是进行中**，桌面录制、真机播放、界面回填、Rust IPC 全部未做。

**进展（2026-11-04，W7 #160）**：

- **登记了但本层不构造请求的通道，绝不会被选成「要上传音频」那一个**。`host_system`（系统识别）
  与 `local_whisper_cpp` 都标 `implemented=False` 并各自写清要谁去做什么；
  `run_asr` 在「没有可用适配器」的分支里给出接法说明（桌面端探测 whisper.cpp / 系统识别，
  把结果经 `audio.hostResult` 回传），而不是留一句「识别失败」。
- **读自己代码时抓到并修掉的 6 处**（都属于「分支不可达 / 门被绕过」这一类，本仓库历史上
  为这类缺陷扣过分）：
  1. `audio_adapters.host_player` 原先 `implemented=False` ⇒ 隐私模式下 TTS 一个候选都选不出，
     `run_tts` 里那条「交给桌面端本机播放、一个字也不上传」的分支**永远不可达**。改成 `implemented=True`
     并注明本层实现的是**文本分段**、真机播放未验收。
  2. `audio_asr_runtime.run_asr` 里有一段对 `local_whisper_cpp` 的早退返回——该通道在选型阶段
     就被排除，**永远进不到这里**。删掉，说明合并进「无可用适配器」分支。
  3. 同文件里 `if not content`（base64 解码后为空）不可达：载荷校验已保证字节数 > 0 且 ≤ 上限。删掉。
  4. `audio_tts_runtime.synthesize` 的隐私门原先写成 `privacy_mode and adapter_id != "host_player"`
     ⇒ **走 host_player 时隐私门被绕过**。改为 host_player 直接拒绝进合成函数、隐私门无条件成立，
     文本分段只由 `run_tts` / `prepare_read_aloud` 负责。
  5. 合成响应只判了「是不是 JSON」，网关回的 **HTML 错误页被当音频收进 segments**。
     新增 `<` 开头的分支，点名「上游回的是 HTML 而不是音频（多为网关错误页）」并带上洗白后的正文摘要。
  6. `audio_barge_in` 里「播报中检测到语音、用户随后说完」那条的原因文案写成「插话未成立」，
     实际语义是**没走到 `barge_confirm` 就结束**，接回动作是 `resume_playback_from_pause` +
     `keep_segment_index`。文案改成「插话未确认成新问题，恢复被打断的播报」，自测同步断言动作。
- **阈值全部标了「配置缺省，非实测」**：`ECHO_GUARD_MS=350` / `MIN_SPEECH_MS_FOR_BARGE=280` /
  `MIN_BARGE_ENERGY=0.18` / `MAX_BARGE_LATENCY_MS=1200` / `MIN_SEGMENT_RATIO_FOR_RESUME=0.7`。
  超时限那条会把「隔了多少 ms / 上限多少」写进原因，并**丢缓冲重来**而不是停在半路。
- **接回（用户说完之后剩下的段落）与主轮次解耦**：只念了个开头（不足 70 %）的那一段
  **整段重念**——从半句接上听不出说了什么；已念过大半的放过，接后面的段；
  `resume_after_turn` 为假（含按停）就不接。本层只交出可用段号，**接不接由调用方判**
  （用户在插话里问的是新东西，有新轮次要答就不该硬接念）。
- **`session_from_dict` 只恢复本层认得的字段**：未知状态回 `idle`、越界段号归一到 0、
  段数 0 归一到 1，未知字段忽略而不是猜。

## 4. 未验收与边界

- **真机麦克风未验收**：音频字节由调用方（桌面端）交进来，本层从不打开录音设备。
- **各家厂商端点的真实报文未验收**：假上游是刻意构造的应答形状（`text` /
  `choices[0].message.content` / `segments[]` / `{"audio_b64"}` / 裸二进制 / HTML 错误页 /
  5xx / 连不上），它**不会比真端点更宽容**，但真端点可能回第四种形状——那时本层会
  如实报「上游响应里没有可懂的转写文本字段（拿到的是 …）」，不会猜字段。
- **打断时序实机未验收**：6 个阈值全是配置缺省，没有一次真实播报插话实测。
- **真机播放未验收**：`host_player` 本层只算「该念哪几段、念什么文本」，播放器在桌面端。
- **界面半边全部未做**（也不在本刀领地）：语音输入按钮、按住说话、识别文本落到输入框光标处、
  朗读开关与进度、打断的界面反馈。⇒ 台账 D-11 三条验收里**「可插入输入框」保持未验收**，
  另两条只能称「引擎层已验」。
- **本刀没有把逻辑接进任何进程入口**：`engine/routes_voice.py` 仍是空 router，
  `src/shared/contracts_voice.ts` 的 `IPC_CHANNELS_VOICE` 仍是空表，
  `src-tauri/src/ipc/voice.rs` 仍按车道约定回 `IPC_LANE_NOT_IMPLEMENTED`。
  **下一半的建议**（三件要一起动才接得通，别只动一件）：
  1. `engine/routes_voice.py` 加 `POST /api/audio/asr`、`/api/audio/tts`、`/api/audio/barge`
     （前缀已在 `routes_lanes.LANE_PREFIXES["voice"]` 登记，`check_lane` 不会判越界；
     端点直接转 `run_asr` / `run_tts` / `audio_barge_in.apply`，配置从 `rl.engine()` 的会话表取，
     与 orchestrate 车道同一写法）；
  2. `src/shared/contracts_voice.ts` 加同名 method、`src-tauri/src/ipc/voice.rs` 加对应分支
     （这两份按 #164 的车道约定是 W7 自己的文件）；
  3. 真机半边：`getUserMedia`/系统录音把 base64 交给 `/api/audio/asr`，播放器消费
     `TtsResult.segments[].audio` 并把进度回灌 `playback_progress`。
  **注意第 1 条会不会要动中心注册表**：`src/shared/ipc-lanes.ts` 不在 W7 领地，
  若 `laneDispatchOf` 需要它登记方法名，那就得走 W4 的注册面或明确重新划领地——
  本刀因此**只做了引擎层，没做端点**，不是遗漏。
