## 0. 说明

### 0.1 本文收录什么

本文收录三类问题：

1. **交付阻断**：没有它就无法对外发布、部署或通过安全评审。
2. **产品缺口**：与 Octop、OpenHuman 对标后，用户会感知到的能力缺失。
3. **工程质量**：不直接面向用户，但会放大故障、拖慢迭代的问题。

不收录纯代码风格问题、无用户影响的重构、以及没有明确验收标准的主观优化。

### 0.2 缺陷分级

| 级别 | 判定标准 | 处理时限 |
| --- | --- | --- |
| P0 | 阻断发布、部署或安全评审；或存在数据 / 密钥 / 越权风险 | 0.2 前必须关闭 |
| P1 | 核心体验或商业闭环缺口；竞品已有且用户会直接比较 | 0.3 前关闭 |
| P2 | 竞争力与效率提升；有替代方案 | 1.0 前评估 |
| P3 | 长尾与打磨 | 按需 |

### 1.2 最关键的五个问题

1. **服务化部署没有闭环。** 引擎直跑与令牌链路已验证，但 Docker 镜像、反向代理、TLS、公网 SSE 都没有真实跑过。当前只能"本机演示"，不能"交付部署"。
2. **服务化没有用户体系。** 一个令牌等于全部权限，无法区分人、无法审计到人、无法做配额。这不是加个登录页能解决的，需要令牌到用户的映射与租户边界。
3. **操作系统级沙箱只覆盖 Windows。** Windows 版 AppContainer 隔离已落地并实测（终端、MCP stdio、ACP），macOS / Linux 与 Hooks 仍是策略沙箱，跨平台安全承诺还不能统一。
4. **IM 通道只对假服务端验证。** Slack、钉钉、企业微信、飞书四条链路都有代码，但没有真实企业应用凭据，线上行为未验收。
5. **跨平台未验证。** Windows 之外没有构建、随包 Python 与安装包验证，市场覆盖被限制在单一平台。

另有两项产品级差距不在"发布阻断"之列，但决定 0.3 能否讲"团队工具"：多 Agent 团队协作（D-34）与结构化长期记忆（D-35）。它们不是加页面能解决的，需要运行时与数据模型配套，详见 §1.3 与附录 C。

## 3. P0 缺陷

### D-01 服务化部署链路未闭环

**现状**

- 引擎可以用 `--web-dir dist` 同端口托管静态前端与 `/api/*`，`/health` 与静态文件免令牌，`/api/*` 需令牌。
- 非回环绑定必须同时有 `TT_ALLOW_REMOTE_BIND=1` 与非空令牌。
- 仓库内有 `tongtian-tauri/deploy/Dockerfile` 与部署说明，但本机没有 Docker，镜像未构建、未运行。
- 真实 Nginx / Caddy 的 TLS、SSE 缓冲、超时、并发未验证。

**缺陷**

部署模板存在，但没有一条经过验证的"从零到可访问"路径。用户按文档操作可能遇到：镜像构建失败、反代缓冲导致 SSE 不流式、TLS 证书链错误、长连接被网关断开。

**影响**

- 无法对外承诺"可部署"。
- 服务化模式的 401 令牌弹窗、CLI 三命令都只在直跑场景验证过。

**实现方案**

1. 在 CI 或独立 Linux 主机上构建镜像，固定基础镜像与依赖版本。
2. 提供两套反代样例：Nginx 与 Caddy；显式关闭 `proxy_buffering`，设置 `proxy_read_timeout` 与 `X-Accel-Buffering: no`。
3. 用自签证书跑通 TLS，再验证公网域名。
4. 增加部署自检脚本：健康检查、静态页、带令牌 `/api/chat`、SSE 首包、断线重连。
5. 把"已验证 / 未验证"写进部署说明，未跑过的组合不得标为支持。

**依赖**：Docker 运行环境、一台 Linux 主机、可解析域名（公网验证）。

**验收**

- 干净主机执行文档步骤，15 分钟内得到可访问地址。
- SSE 首包 ≤ 2 秒，连续 10 分钟不被反代断开。
- 错误令牌返回 401，正确令牌可完成一次对话。
- 部署自检脚本全绿；失败时输出可定位的中文原因。

### D-02 服务化无用户体系，单令牌全权限

**状态**：最小版已落地（账号服务 JWT 声明与吊销、引擎侧 JWT 校验、按人审计与用量）；完整版（组织隔离、配额硬停、管理后台）未开始。

**现状（最小版改造前）**

- 服务化模式只有一个 `TT_ENGINE_TOKEN`，持有令牌即拥有全部能力。
- 没有用户、角色、租户、配额归属。
- 账号服务只服务桌面端登录，不参与引擎鉴权。

**缺陷**

单令牌无法回答"是谁在用""能用多少""出了事找谁"。这会让服务化模式停留在个人试用，无法进入团队或企业。

**影响**

- 无法做按人配额、审计到人、权限分级。
- 令牌泄露等于全部数据与执行能力泄露。
- 无法支持多团队隔离。

**实现方案（最小版，M1）**

1. 引擎接受账号服务签发的短期 JWT，校验签名、过期、受众。
2. 令牌声明包含 `sub`（用户）、`org`（组织）、`role`、`quota`。
3. 每次请求把 `sub` 写入审计与用量；未知用户拒绝。
4. 保留静态令牌作为单机兼容模式，但启动时明示"无用户隔离"。

**完整版（M3）**

1. 组织 / 成员 / 角色模型；邀请与移除。
2. 租户级数据隔离：工作区、会话、知识库按 `org` 分区。
3. 配额与预算按组织 / 用户两级；超限硬停。
4. 管理后台：成员、配额、模型、审计。

**依赖**：账号服务扩展、数据库迁移（增量）、管理后台。

**进展（2026-10-28）**：账号服务（`tongtian-server`）已完成最小版 JWT 声明与吊销能力——access/refresh 令牌携带 `iss`/`aud`/`sid`/`org`/`quota`；access 令牌绑定 `sessions.id`，退出、刷新轮换或管理员强制下线后立即失效；新增管理员接口 `PATCH /api/v1/admin/users/{uid}`（设置组织与配额，返回 `sessionsRevoked`）与 `POST /api/v1/admin/users/{uid}/revoke-sessions`；`users` 表通过增量迁移增加 `org_id`/`quota_json`。引擎侧（`tongtian-tauri/engine`）已接入同一套 JWT：校验 HS256 签名、`exp`、`iss`、`aud`、`type=access`、`sub`、`sid`，支持 `TT_ENGINE_ALLOWED_USERS` 白名单；每个 `/api/*` 请求记录 `sub/org/role/sid/方法/路径/状态/耗时/IP`，`GET /api/audit` 可查（普通用户仅自己、管理员全部），可选用 `TT_ENGINE_AUDIT_LOG` 追加 JSONL；模型用量台账按 `sub` 归集，`/api/usage` 与 `/api/usage/report` 支持按用户过滤并返回 `users` 汇总。静态 `TT_ENGINE_TOKEN` 保留为应急通道，非回环绑定允许“静态令牌或 JWT 密钥”二选一。服务端与引擎自测覆盖签发字段、`aud`/`iss`/`type`/`sid` 反例、白名单、审计隔离与落盘、用量归属、绑定准入。**仍未完成**：组织级数据隔离（工作区、会话、产物按 `org` 分区）、配额硬停、账号侧吊销的实时内省（引擎只按 `exp` 失效，最长 15 分钟），因此“两个用户互相看不到对方会话与产物”的验收项尚未满足。

**验收**

- 两个用户使用同一引擎，互相看不到对方会话与产物。**未满足**：引擎尚未按 `org` 分区，审计与用量的可见范围收窄不等于数据隔离。
- 审计可按用户筛选；用量可按用户聚合。**已满足**（引擎自测覆盖普通用户只看自己、管理员看全部、用量按 `sub` 汇总）。
- 删除用户后其令牌立即失效。**部分满足**：账号服务侧签发即绑定 `sessions.id`，吊销即时生效；引擎不内省账号服务，只按 `exp` 失效，最长 15 分钟窗口。
- 超配额请求返回明确错误码，不执行任务。**未满足**：配额目前只是令牌声明与展示值，引擎未做硬停。

### D-03 无操作系统级沙箱

**状态**：进行中。Windows 版已落地并通过实机验收；macOS / Linux、Hooks 与写暂存审批未完成。

**现状**

- 两层隔离同时存在：
  - 策略沙箱：工作目录边界、工具白名单 / 黑名单、L0 只读 / L1 / L2 执行等级、路径黑名单，在工具调用点拦截并把中文原因回给模型、写审计。
  - 系统隔离（Windows 10/11 AppContainer）：终端会话、MCP stdio 服务、ACP 外部 Agent 的真实子进程以容器令牌启动，越界写入与读取数据根密钥由系统 ACL 拒绝。
- 启动方式是主程序的隐藏子命令 `--tt-sandbox-run`：单二进制、不进 WebView、在 Tauri 初始化前返回，避免 sidecar 的打包与签名分叉。
- 配置落 `security_policies.system_sandbox`；启用时真实创建 profile，创建失败就拒绝启用，不保存一份永远不生效的"已开启"。
- 安全设置页把两层分开标注：策略沙箱按工作区展示 L0/L1/L2，系统隔离展示请求 / 平台支持 / 实际生效三栏与未生效原因。

**已实现要点**

- 容器 profile 固定为 `TongTian.Agent`，同一台机器复用，不每次启动重建。
- 工作区授予读写，沙箱临时目录可写；会话库 `tongtian.db`（含 `-wal` / `-shm`）、配额台账、审计导出目录、意识目录 `TONGTIANWORK_HOME` 显式拒绝。
- 环境块过滤：名字含 token / secret / password / api_key / access_key 的变量不进入沙箱；连接器显式配置的变量名通过 `--allow-env` 保留。
- 网络能力整体授予：关闭时能力数为 0，开启时授予 internetClient 组。
- 子进程挂 Job Object（`KILL_ON_JOB_CLOSE`），父进程退出即回收整棵进程树。
- ACL 授予带缓存（`%LOCALAPPDATA%\TongTianSandbox\<profile>\grants.txt`），同一路径只传播一次；`TT_SANDBOX_NO_CACHE=1` 可强制重做。
- 引擎侧 `engine/sandbox_launcher.py` 统一套壳；配置了隔离却找不到启动器时一律拒绝执行，不静默降级。

**未完成**

- macOS / Linux 的系统级隔离（见 D-05）。
- Hooks 命令仍以应用权限执行：它们是用户逐条放行的本机自动化，且逐文件授权大目录的成本不可接受。
- 文件写入先落暂存区、审批后合并与 diff 预览。
- 按进程 / 工具的出域域名白名单，目前只有整组开关。
- 包管理器启动的 MCP 服务需要补充可读目录，界面上还没有引导。

**实现方案（剩余）**

1. macOS 用 seatbelt、Linux 用 bubblewrap 实现与 Windows 同协议的启动器，主程序按平台分发。
2. Hooks 纳入隔离：先解析出脚本路径，只对脚本所在目录授予只读，避免整树传播。
3. 写操作走暂存区 + diff 审批，与现有工具审批网关合并。
4. 出域白名单下沉到系统隔离层，与策略沙箱的域名清单共用一份配置。

**验收**

| 验收项 | 结果 |
| --- | --- |
| 越界写文件被系统层拒绝 | 通过：工作区外写入 `PermissionError`，文件未生成 |
| 子进程无法读取数据根中的密钥文件 | 通过：读取临时数据根内的会话库与密钥文件 `PermissionError` |
| 关闭网络后无法访问外网 | 通过：公网连接报 `WinError 10013`；开启后公网可达 |
| 安全设置页显示真实等级 | 通过：桌面版实机点开关，请求 / 生效 / 未生效原因随真实状态变化；关闭后回读配置为 `false`；平台不支持或未启用时对应开关禁用 |

自动化覆盖：

- `src-tauri/tests/sandbox_acceptance.rs`：真实进程验收越界写、密钥读取与断网。
- `tests/integration/engine_sandbox_wrapper_selftest.py`：套壳命令行结构、启动器缺失时拒绝执行、终端接入。
- `cargo test --lib sandbox::`：参数解析、环境块过滤、敏感路径、状态计算。
- `tests/unit/security/sandbox-system-contract.test.ts`：设置通道按对象透传（关闭必须落 `false`）、启用前先建 profile、启动恢复、设置页三栏与禁用条件。

**已知边界**

- AppContainer 的网络隔离包含回环与局域网：即使开启出网，容器内进程仍连不上 `127.0.0.1` 与局域网地址，需要管理员配置 loopback exemption。沙箱内的终端访问本机服务会失败。
- 首次给大目录授予工作区权限要逐文件传播 ACL，耗时与文件数成正比；之后走缓存。浏览器预览环境不提供系统隔离，设置页如实显示不支持。
- 系统隔离只对新启动的引擎进程生效，改完设置需要重新开始任务。

### D-04 IM 四通道仅假服务端验证

**现状**

- Slack、钉钉、企业微信、飞书四个通道均有实现，包含长连接、消息收发、会话映射。
- 测试使用本机假服务端（`fake_slack.py` / `fake_dingtalk.py` / `fake_wecom.py` / `fake_feishu.py`），验证握手、回执、消息循环与回贴。
- 没有真实企业应用凭据，未验证平台审核、权限范围、频率限制、消息格式差异。
- 四条通道都只处理文本：Slack 只取 `message` 文本；钉钉 / 飞书只接受 `message_type == text`；企业微信对 image/file/video/voice 直接忽略（代码注释说明需要 AES 解密或转写，当前未实现）。出站也只发文本，没有图片 / 文件、typing、逐通道限流与群可见性策略。
- Octop Gateway 已覆盖 10 个平台，统一 `ContentPart`（text / image / video / audio / file）、媒体后端、逐通道限流 / 超时 / typing、群 `visibility` / `activation` 策略与同类型多实例隔离。任我行即使凭据可用，也只能文本收发。

**缺陷**

"支持四个 IM 通道"目前是代码事实，不是产品事实。真实环境可能出现：应用审核不通过、事件订阅配置错误、消息卡片格式不兼容、长连接被平台限流。即使审核通过，纯文本能力也无法覆盖图片、文件、群聊 @ 与通知场景，通道深度与 Octop 不在同一层。

**影响**

- 企业交付时无法承诺开箱即用。
- 出问题后缺少平台侧排查经验。

**实现方案**

1. 为每个通道建立真实测试租户，至少完成一个通道的端到端验收。
2. 记录每个通道的：应用类型、权限范围、事件订阅、回调 / 长连接配置、消息格式限制。
3. 增加通道健康检查：凭据有效性、连接状态、最近一次收发时间。
4. 对未验证通道在界面上标注"未验证"，不显示"已支持"。
5. 把假服务端测试保留为回归测试，但不能替代真实验收。
6. 文本闭环验收后，按 D-41 补图片 / 文件、群策略、限流与 typing；未实现前在界面标注"仅文本"，不得宣称支持媒体消息。

**依赖**：四个平台的企业应用管理权限、审核周期、测试群。

**验收**

- 至少一个通道在真实企业租户中完成"发消息 → Agent 执行 → 回贴结果"。
- 断线后自动重连，重连期间不丢消息。
- 凭据错误、权限不足、频率限制都有中文提示。
- 其余通道明确标注验证状态与消息类型；仅文本通道不得宣称支持图片 / 文件。

### D-05 macOS / Linux 未验证

**现状**

- 开发与验证集中在 Windows 10/11 + WebView2。
- 随包 Python 脚本只处理 Windows embeddable amd64。
- macOS / Linux 的构建、钥匙串、系统权限、安装包、通知与角标均未验证。

**缺陷**

跨平台是桌面产品的基本预期；当前只有 Windows 可用，且没有证据说明其他平台会在何时可用。

**影响**

- 市场覆盖被限制在单一平台。
- 企业客户中 macOS 占比较高时无法交付。

**实现方案**

1. 先做"可构建"：CI 增加 macOS / Linux 构建任务，修复编译与打包错误。
2. 再做"可运行"：Python 运行时按平台准备；钥匙串适配；系统权限入口适配。
3. 最后做"可验收"：每个平台跑核心链路（登录、对话、产物、执行面）。
4. 明确平台能力矩阵：哪些执行面仅 Windows，哪些跨平台。

**依赖**：macOS / Linux 构建机、代码签名证书（分发）、平台测试设备。

**验收**

- 两个平台均能构建出安装包并启动。
- 核心链路在各自平台通过。
- 平台差异在文档与界面中明示。

## 4. P1 缺陷

### D-06 协作无实时推送，10 秒轮询

**现状**：协作页每 10 秒拉取一次项目与任务；成员变更、评论、结果回报都有延迟。

**影响**：多人同时操作时看到旧状态；评论像"留言板"而不是协作。

**方案**：账号服务增加 SSE 或 WebSocket 通道；客户端订阅项目事件；断线重连并按游标补拉。保留轮询作为降级。

**验收**：两人同时操作，状态在 1 秒内同步；断网恢复后不丢事件。

**进展（2026-10-28）**：服务端已增加 `GET /api/v1/projects/{id}/events`（按 `since` 增量拉取）与 `GET /api/v1/projects/{id}/events/stream`（SSE，500ms 轮询、15 秒心跳、支持 `Last-Event-ID` 续传、成员被移除时关闭）。服务端测试已覆盖游标、权限与实时推送；桌面端仍是 10 秒轮询，待接入订阅。

**工作量**：2–3 人日。

---

### D-07 市场只安装不更新、无撤销

**现状**：客户端只有安装命令；服务端有版本与更新时间，但没有客户端更新检查，也没有撤销 / 下架列表。

**影响**：已安装的恶意或有缺陷版本无法远程止损；用户长期停留在旧版本。

**方案**：安装记录版本与哈希；启动或手动检查更新；支持"固定版本"；服务端增加撤销列表，客户端命中后禁用并提示卸载。

**进展（2026-10-28）**：服务端已增加管理员版本撤销 / 恢复接口（`POST /api/v1/admin/items/{type}/{id}/versions/{version}/revoke|unrevoke`）与公开下架列表 `GET /api/v1/revoked`；撤销版本从"最新版本"计算中排除，下载与 MCP 配置接口返回 `410 ITEM_REVOKED`，撤销字段以增量迁移写入 `item_versions`。服务端测试覆盖权限、幂等、最新版本回落与恢复；客户端安装记录、更新检查与撤销禁用尚未接入。

**验收**：发布新版本后客户端可检测并升级；撤销后已安装包被禁用且不可执行。

**工作量**：1–1.5 人日。

---

### D-08 插件 / 套件无代码执行沙箱

**现状**：插件模块只做 `plugin.json` 校验与模板生成；套件只消费 `commands` 与包内 `SKILL.md`；`mcpServers` / `hooks` / `agents` 等字段被忽略并列出。

**影响**：无法支持真正的插件生态；一旦开放代码执行，现有边界不足以保证安全。

**方案**：定义插件能力清单（命令、技能、MCP、Hook）；默认只允许声明式能力；代码执行走独立进程 + 权限清单 + 资源上限；安装时展示将获得的权限。

**验收**：插件无法访问未声明路径与网络；超资源被终止；卸载清理干净。

**工作量**：8–12 人日。

---

### D-09 知识库仅词法检索

**现状**：SQLite FTS5 + 中文单字 / 二元组 + 英文词元；无 embedding、无 rerank、无 OCR；PDF 只提取可读文本。这是知识库检索，不等同于长期记忆；记忆的结构化与召回问题单列 D-35。

**影响**：同义表达召回差；扫描件无法检索；长文档片段排序不稳定。

**差距**：Octop 有独立的知识库 RAG（语义检索、部署内共享），其记忆系统另有结构化事实与召回预算；两者不要混为一谈。任我行知识库的确定差距是语义召回、扫描件与排序；长期记忆差距见 D-35。

**方案**：保留 FTS5 作为兜底；增加可选向量索引（本地 embedding 模型或云端）；增加 rerank；扫描件走 OCR 或明确提示"未提取到文本"。如果引入向量索引，与 D-35 共用 embedding 与预算策略，避免维护两套召回。

**验收**：同义查询命中率相对基线提升；无向量模型时自动降级且提示；扫描件有明确状态。

**工作量**：10–15 人日。

---

### D-10 无可视化工作流编排

**现状**：只有单任务 cron；无节点编排、条件分支、人工审批节点、失败重试策略。

**影响**：复杂重复任务只能写成长提示词，不可复用、不可观测。

**方案**：先做线性步骤 + 条件分支 + 审批节点；再考虑画布。工作流定义可版本化、可导入导出。

**验收**：一个包含"抓取 → 摘要 → 审批 → 生成文档"的工作流可保存、复用、查看每次运行。

**工作量**：15–20 人日。

### D-11 无语音输入与实时语音

**现状**：设置中有"语音输入"入口，标注"尚未提供"；无 ASR、无 TTS、无实时语音会话。

**影响**：移动与免手操作场景缺失；与 OpenHuman 的差距明显。

**方案**：先做按住说话转文字（系统或云端 ASR）；再做回复朗读；实时语音作为独立项目评估。

**验收**：语音输入可插入输入框；失败有原因；隐私模式下不上传音频。

**工作量**：10–20 人日。

### D-12 无自动更新渠道

**现状**：设置页如实显示"未配置更新渠道"，更新方式为覆盖安装。

**影响**：安全修复无法及时触达；用户版本碎片化。

**方案**：接入 Tauri updater 或自建更新清单；签名校验；灰度与回滚；离线环境支持手动包。

**验收**：新版本可检测、下载、校验、安装；失败可回滚；无更新渠道时界面不放假按钮。

**工作量**：5–8 人日。

### D-13 应用快照与浏览器上下文接力缺失

**现状**：应用快照入口存在但明确"尚未提供"；浏览器会话不共享用户登录态与标签页上下文。

**影响**：用户需要手工复制粘贴上下文；浏览器任务从零开始。

**方案**：应用快照先做"用户主动触发 + 预览 + 确认后上送"；浏览器接力先做受控会话内的标签页与登录态复用，明确隔离边界。

**验收**：快照内容上送前可见可取消；浏览器任务可复用已授权会话；机密级内容不上送。

**工作量**：2–3 人日（快照）+ 后续浏览器接力单列。

### D-14 配额 / 预算无 UI 与告警

**现状**：Rust 侧有配额门与档位跃迁事件，运行中可因预算耗尽转 `budget_paused`；前端没有配置入口与可视化。

**影响**：用户不知道为什么任务被暂停；无法提前设置预算。

### D-15 失败步骤不能单步重试

**状态**：部分实现。Rust harness 续跑可跳过已完成工具；界面仍不能只重试失败步骤。

**现状**：失败后可重新生成整轮；客户端内嵌 Rust harness 的检查点已记录工具签名，续跑时通过 `previous_record` / `skip_previous` 跳过同签名且已完成的工具，`resumable` 会在取消或异常中断时保留快照。但界面没有"重试此步 / 从此步继续"入口，非幂等工具没有二次确认，Python 引擎路径也没有同等单步控制。

**影响**：一次工具超时仍可能导致整轮重跑；用户无法判断哪些步骤会重放，浪费 token 与时间。

**方案**：为每个步骤保留输入与工具结果；UI 提供"重试此步"与"从此步继续"，并展示将重放的步骤；幂等工具直接重放，非幂等工具要求确认。运行时基础见 D-40。

**验收**：单步失败后可只重试该步；已完成步骤不重复执行；非幂等操作有确认；续跑前可见将重放的步骤。

**进展（2026-10-28）**：检查点同签名跳过与 `resumable` 已落地并有 Rust 单测；界面入口与非幂等确认未开始。

**工作量**：3–5 人日。

### D-18 性能与 token 效率落后

**现状**：普通任务由客户端内嵌 Rust harness 执行，连接器、浏览器、电脑操作、知识库、专家套件、Hooks、工具审批、出站脱敏与 ACP 仍交给 Python + AgentScope 引擎。Python 路径有上下文预算压缩（`COMPRESSION_RATIO=0.6`、预留 512 tokens）与 MCP 工具懒加载（`search_tools`）；Rust harness 没有压缩 / 摘要，长任务更容易撞窗口。两条链路都没有公开的冷启动、内存、token 对比数据。OpenHuman 公开宣称单进程 Rust、68MB 峰值、2.6 倍更少 token。

**差距**：Octop 的成本优势来自多处——多级 DOM、渐进式工具加载、记忆召回预算与分层记忆；任我行的 Rust 默认路径避免了每次走 Python 冷启动，这是本地优势，但不能当成整体 token 优势。没有基准就不能判断哪条链路更省。

**影响**：成本与响应速度处于劣势；长任务在默认路径上可能提前失败；大规模部署时资源开销高。

**方案**：先建立可复现的基准（冷启动、首包、单任务 token、峰值内存），Rust 与 Python 两条链路分别测；再做低风险优化：引擎预热、工具结果截断与摘要、系统提示精简、按任务裁剪工具集、Rust harness 上下文压缩（D-40）；架构级替换需单独评估。

**验收**：两条链路都有可重复基准；优化后单任务 token 与首包时延有可量化下降；不牺牲产物质量。

### D-34 多 Agent 团队协作缺失

**状态**：待处理。

**现状**

- 专家只是注册表条目：`engine/expert_runtime.py` 保存 id、名称、描述、提示词、模型与技能白名单；没有独立工作区、独立检查点或团队编制。
- `engine/subagent_runtime.py` 提供进程内子 Agent：单任务最多 4 个、3 路并行、6 轮迭代、1 次续跑、300 秒超时；子 Agent 与主任务共享工作区，不能继续嵌套，结果合并回主任务事件流。
- PRD 中 EXP-03 为"有限实现"：只有角色配置与结果汇总；EXP-07（团队过程可视化）未实现。

**差距**

Octop 的 AgentTeams 把团队做成一种专家：主持人 `kind=team`，成员仍是普通专家。主持人不做专业工作，只通过异步 inbox 派工；同一成员串行、不同成员并行；成员回复直接上群聊时间线并带 `speaker_agent_id`；每个成员使用 `主thread~成员id` 的独立检查点和工作区；成员失败会回叫主持人；停止只停主持人本轮；团队成员在途时禁止移出或删除。任我行目前没有团队实体、房间、异步派工、成员独立检查点、失败回叫与群聊转播，子 Agent 只是主任务内部的临时并发。

**影响**

- 复杂任务仍是"一个 Agent + 临时子任务"，无法形成可复用、可观察、可恢复的分工。
- 用户看不到谁在说话，也无法只重跑某个成员。
- 多 Agent 只能作为内部实现细节，不能作为产品能力交付。

**实现方案**

1. 团队 = 主持人专家 + 工作区 `manifest.json`（`kind=team`、成员 id）；成员仍是普通专家，可加入多个团队。
2. 房间 id 使用主持人会话 id；成员检查点使用 `房间~成员`；成员使用自己的会话目录，不共享主持人工作区。
3. 增加异步派工工具：主持人一次可并行派多人；同一成员按 inbox 串行；成员完成后回叫主持人总结并判断是否收工。
4. 房间事件流带 `agent_id` / `speaker_agent_id`；桌面端增加成员条、团队徽章与说话人气泡；停止只停主持人。
5. 团队在途任务写入增量表（`team_jobs`），重启后标记 `interrupted` 并可重派，不静默丢失。
6. IM 通道只绑主持人；派工成功先推"已请某成员处理"，成员收口后推带姓名的消息。

**依赖**：D-40 的检查点与恢复能力；D-41 的通道转播；D-35 的团队记忆（可选）。

**验收**

- 创建含 2 名成员的团队，主持人一次并行派工两人。
- 两名成员的回复按说话人上墙；主持人给出总结。
- 成员各自检查点独立；重启后未完成任务显示中断，不标记成功。
- 停止只停主持人；成员继续跑完并回叫。
- 团队编制重启后保留；在途成员不能被移出或删除。

**工作量**：12–18 人日。**里程碑**：M2。

**验收**

### D-40 默认 harness 的长任务恢复与上下文治理不足

**状态**：待处理；检查点续跑已有基础。

**现状**

- 普通任务默认由客户端内嵌 Rust harness 执行：两阶段计划审批、工具审批、JSON 检查点（消息、元数据、工具记录）、`previous_record` / `skip_previous` 同签名工具跳过、`resumable` 标记、最大迭代数；内置 `view_text_file` / `write_text_file` / `insert_text_file` / `use_skill`。

**差距**

**影响**

- 长任务在默认路径上更容易失败或成本失控。
- 工具审批后重启无法精确续跑，用户需要重复确认。
- 模型故障转移与多 Agent 团队缺少运行时基础。

**实现方案**

1. Rust harness 增加确定性上下文压缩：保留系统提示、最近回合、工具结果摘要与未完成审批；按 token 预算触发，摘要写入检查点。
2. 工具审批落检查点；重启后从待审批工具继续，已完成工具按签名跳过，并在界面展示将重放的步骤。
3. 线程内切换 provider：保留规范消息历史，按新 provider 重新编码；工具 schema 不兼容时明确提示。
4. 检查点按 Agent / 团队分目录；为团队成员提供独立检查点。
5. 对支持会话复用的 MCP 传输保持长连接；工具超过阈值时按需加载 schema。
6. 建立长任务基准（100 轮、30 个工具、审批中断），记录 token、首包与恢复耗时。

**依赖**：D-15、D-18；D-34 依赖本项的团队检查点。

**验收**

- 100 轮任务在模型窗口内完成，关键决策与审批不丢。
- 工具审批时退出应用，重启后从待审批处继续，已完成工具不重复执行。
- 线程内切换模型后可继续对话，历史不丢。
- 30 个 MCP 工具只加载被检索到的 schema。
- 失败 / 中断的任务不会被标记为完成。

**工作量**：10–15 人日。**里程碑**：M2。

### D-43 存储归属未固化，引擎用量台账不落盘

**状态**：待处理。

**现状**

- 桌面端 `{TONGTIAN_HOME}/t.db` 有 17 张表（任务、消息、审计、`model_usage`、MCP、钩子授权等），只由 Rust 主进程打开。
- 服务端 `data/market.db` 存账号、市场与项目，只由服务端进程打开，不接收也不查询客户端用量。
- 引擎知识索引单独成库；用量台账 `UsageLedger` 只在进程内字典累计，没有落盘，也没有上报接口。
- 三条边（桌面→服务端、引擎→服务端、引擎→桌面）只有路径约定，没有归属约束，也没有测试拦住越界访问。

**影响**

- 引擎侧跑的对话（浏览器直连、IM、CLI、定时任务）重启后用量消失，配额与计费没有依据。
- 同一用户存在两份口径：桌面 `model_usage` 与引擎内存台账互相矛盾。
- 跨库直连没有护栏，接远程工作区或多租户部署时容易越界。

**实现方案**

1. 引擎用量落盘为独立台账文件：按 `subject + model + day` 增量追加，启动时载入，带 schema 版本。
2. 对外只提供一个合并视图：桌面 `model_usage` 为主，引擎台账按同样的键累加补入，不覆盖存量行。
3. 服务端增加用量接收与按用户查询接口（JWT 到人），只做接收与聚合，不读客户端库文件。
4. 补归属契约测试：引擎与服务端源码不得出现 `t.db`，桌面端不得写 `market.db` 路径；新增跨库访问时测试失败。
5. 路径定义只保留一份常量，PRD 6.5 与代码同源，避免文档和路径两处漂移。

**验收**

- 引擎进程重启后用量不丢，日聚合与重启前一致。
- 同一任务在桌面与引擎各跑一次，合并视图口径一致且不重复计数。
- 归属契约测试能在有人新增跨库访问时失败。
- 服务端按用户查到的用量与客户端合并视图一致。

**依赖**：D-02。**工作量**：3–5 人日。**里程碑**：M2。

## 5. P2 / P3 缺陷

### D-23 多账号与组织 / SSO（P2）

当前单账号；无组织、无 SSO、无 SCIM。方案：账号服务增加组织模型，桌面端支持切换账号；SSO 先做 OIDC。工作量 10–15 人日。

### D-24 移动端缺失（P2）

无 iOS / Android 客户端，也无移动端只读视图。方案：先做 Web 响应式只读 + 通知；再评估原生。工作量 20–30 人日。

### D-25 无障碍与主题不完整（P2）

基础键盘可用，但未做 WCAG 审计；主题只有设计令牌，无完整深浅色与密度切换。方案：键盘路径、焦点可见、对比度、读屏标签逐项验收。工作量 5–8 人日。

### D-26 产物版本历史与回滚缺失（P2）

产物覆盖写入，无版本。方案：每次生成保留版本与 diff；可回滚；配额清理旧版本。工作量 5–8 人日。

### D-27 审计防篡改与合规报告缺失（P2）

审计为本地追加文件，可被本机用户修改；无合规报告导出。方案：哈希链 + 可选远端归档；合规模板导出。工作量 8–12 人日。

### D-28 无遥测与崩溃上报（P2）

线上问题不可见。方案：默认关闭、显式同意、可查看将发送的内容；崩溃本地留存并提示导出。工作量 3–5 人日。

### D-29 远程与对象存储工作区缺失（Docker / SSH / S3 / COS / PostgreSQL）（P2）

仅本地目录；无 Docker / SSH 执行器，也无 S3 / COS / PostgreSQL 工作区后端。Octop harness 的工作区可在 Local / S3 / COS / PostgreSQL 间切换，并提供 Docker sandbox 工作区；任我行换机器或接远程算力只能手工同步文件。方案：工作区后端抽象；先做 S3 / COS 对象存储与 Docker / SSH 执行器；凭据进钥匙串；资源与网络限制；远程文件操作审计，与 D-03 的沙箱边界共用配置。验收：不换 Agent 配置即可切换工作区；远程操作可审计；凭据不落配置文件。工作量 10–15 人日。

### D-36 浏览器缺标签页、DOM 分级与录制回放（P2）

**现状**：Rust `src-tauri/src/browser/mod.rs` 与 Python `engine/browser_use.py` 都走 CDP 直连，动作只有 `open` / `snapshot` / `click` / `type` / `select` / `scroll` / `screenshot` 七种；只有一个 `root/profile`，没有标签页管理、DOM 分级、录制回放、命名 profile、MCP server。浏览器上下文接力另见 D-13。

**差距**：Octop Browser 提供约 20 个动作（含 new/switch/close tab、hover、press、wait、evaluate），多级 DOM（minimal / interactive / full / structured），录制 → 语义步骤 → draft skill → 回放，MCP stdio server 与命名 profile。其主仓 README 仍把"浏览器技能录制"列为待打磨，说明独立能力已有、主产品集成度有限；任我行则完全没有。

**影响**：复杂页面容易点错或超时；重复流程每次重新推导；外部 Agent 无法复用浏览器能力。

**方案**：补标签页、hover / press / wait / evaluate；默认只给 interactive DOM，按需展开 structured；录制时注入脚本并对密码等字段脱敏，生成 draft skill 后必须人工确认才可启用；命名 profile 隔离登录态；提供默认关闭的 MCP stdio server。

**验收**：录制 5 步流程后生成草案技能，改一个输入可回放；两个 profile 登录态互不影响；同一页面 interactive DOM 的 token 明显低于 full；录制不保存密码明文；标签页操作可用。

**依赖**：D-13、D-38。**工作量**：8–12 人日。**里程碑**：M3。

### D-37 CLI 管理面过窄（P2）

**现状**：`scripts/tt-cli.mjs` 只有 `health` / `chat` / `doctor`，令牌只读 `TT_ENGINE_TOKEN`，默认 `http://127.0.0.1:18000`；`scripts/agentctl.py` 提供平台层 `status` / `skills` / `mcp` / `channels` / `chat` / `im` / `schedule` / `init`，但平台层默认关闭、未接桌面主链路。

**差距**：Octop CLI 覆盖 `chats`（CRUD + REPL + send）、`agent`（create / start / stop / reload）、`channel`、`cron`、`skills`、`backup`、`update`，支持 offline / attach / embedded 三种传输与 `--json`，并可登录换取 JWT。任我行没有会话管理、Agent 生命周期、通道配置、备份恢复与更新检查的 CLI。

**影响**：无头 Linux、服务端运维、自动化脚本与故障恢复都只能靠网页或手工改文件；平台层 CLI 又不可用于正式环境。

**方案**：把 `tt-cli` 扩成正式管理面：会话列表 / 查看 / 删除与 REPL；专家 / Agent 启停与重载；通道状态与测试；定时任务列表与立即执行；数据根备份 / 恢复；更新检查依赖 D-12。所有命令支持 `--json`，令牌只从环境变量或钥匙串读取。

**验收**：无头环境可用 CLI 启动 Agent、发一条对话、查看会话并停止；`--json` 输出可被脚本稳定解析；备份 / 恢复在测试数据上往返一致；命令行与日志不出现令牌明文。

**依赖**：D-19、D-12。**工作量**：5–8 人日。**里程碑**：M2 / M3。

### D-38 技能无共享池与统一注册表（P2）

**现状**：Rust 侧技能是 `SKILL.md` 目录（frontmatter 名称 / 描述），套件用 `plugin.json` 带 `commands` 与内置技能，市场有 Ed25519 签名与静态风险扫描；Python 平台层另有一套 YAML 技能（提示词、工具白名单、上下文策略、窗口配置），默认关闭。两套注册表语义不同，技能按专家重复安装，没有共享池、统一依赖检查、成功任务蒸馏或自动更新。

**差距**：Octop 的技能由 deepagents 技能中间件按 Agent 启停，共享技能 / 子 Agent 池已上线；自进化（把日常对话蒸馏为技能）与插件市场仍是路线图。任我行连共享池与统一注册表都没有，且市场只安装不更新（D-07）、无代码沙箱（D-08）。

**影响**：同一个技能在多个专家下重复维护；用户无法积累可复用能力库；Rust 与 Python 两条链路各认一套技能，行为不一致。

**方案**：定义一份可被 Rust harness 与 Python 平台共同消费的技能清单（名称、描述、提示词、工具、上下文、窗口、来源、版本）；在数据根建立共享池，专家按 id 引用并单独启停；为既有 `SKILL.md` 与 YAML 提供只读适配，不移动或删除原文件；成功任务与浏览器录制可生成 draft skill，必须人工审核后才启用；启用前检查技能 / MCP / 工具依赖。

**验收**：一个技能从共享池同时启用给两个专家，改一次两边生效；停用立即影响两边；既有技能迁移后仍可加载；draft skill 不会自动启用；缺依赖时中文提示且不静默跳过。

**依赖**：D-08、D-36。**工作量**：6–10 人日。**里程碑**：M2 / M3。

### D-39 MCP 连接器生态与接入模式不足（P2）

**现状**：Rust 侧支持 stdio / streamable HTTP / SSE，OAuth PKCE（令牌、刷新、撤销）、工具级 allowlist、探测与工具列表；没有 resources / prompts。Python 平台层有 `McpCatalog`、客户端池与内置 `mcp_catalog.yaml`，默认关闭。连接器市场可安装，但每个服务仍要手工填配置。

**差距**：Octop 内置 29 个连接器，提供 remote / gateway / internal 三种 MCP 模式、OAuth 一键授权、托管持久会话与工具按需加载。任我行没有连接器目录、没有 gateway / internal 模式，OAuth 逐服务手工配置，健康检查与自动重连也以手动为主（PRD MCP-07）。

**影响**：企业 SaaS 接入成本高；用户不知道要填哪些 scope / 回调；连接器工具一多就挤占上下文；同一连接器无法按专家做不同工具白名单。

**方案**：建立连接器目录（先覆盖办公 / 知识 / 协作至少 8 个），写清鉴权类型、scope、文档与图标；一键 OAuth（PKCE、刷新、撤销，凭据进钥匙串）；先实现 remote 与 gateway 两种模式，internal 后置；统一 Rust / Python 的连接器注册表；健康检查、退避重连与中文错误映射；工具按专家 / 技能 allowlist 暴露。

**验收**：5 个连接器可通过 OAuth 添加，无需手写 JSON；令牌过期可刷新，撤销后立即失效；停用连接器后工具不可调用；同一连接器可给两个专家不同工具白名单；失败原因中文可读。

**依赖**：D-08。**工作量**：8–12 人日。**里程碑**：M2 / M3。

### D-41 IM 网关缺媒体、群策略与限流（P2）

**现状**：四条通道的入站事件只有 `kind` / `text` / `conversation_id` / `user_id` / `message_id`，出站 `send(creds, conversation_id, text)` 只发文本；Slack 只取 `message` 文本，钉钉 / 飞书只接受 `message_type == text`，企业微信对 image / file / video / voice 直接忽略。没有媒体后端、群可见性 / 激活策略、逐通道限流、超时与 typing。新增的 platform `ChannelGateway` 默认关闭，未接桌面主链路。

**差距**：Octop Gateway 用统一 `ContentPart` 承载 text / image / video / audio / file，`MediaBackend` 存附件，逐通道限流 / 超时 / typing，`push_text` / `push_content` / `push_to_all` 主动推送，群 `visibility` / `activation` 与同类型多实例隔离。任我行只有纯文本单实例。

**影响**：用户不能把截图 / 文件直接发给 Agent；群里要么频繁误触发，要么完全不响应；平台限流时没有退避，容易被封；企业场景无法按群配置可见范围。

**方案**：把入站 / 出站事件扩为 `ContentPart`，媒体下载 / 上传带大小与类型限制并落沙箱目录；增加群 `visibility` / `activation` / 历史窗口配置；逐通道限流、超时、typing 与 429 退避；同类型多实例按 `channel_id` 隔离凭据与状态；把 platform `ChannelGateway` 接到桌面主链路并保留旧通道适配器。

**验收**：至少一条真实通道可收发图片或文件；群内 @ 触发、非 @ 按策略处理且不重复回复；429 时退避并显示中文状态；两个同类型通道实例互不影响；支持 typing 的平台显示输入状态。

**依赖**：D-04。**工作量**：8–12 人日。**里程碑**：M3。

### D-44 模型档位无服务端供给（P2）

**现状**：模型选择完全在客户端：`models.json` 条目加任务级 `modelConfig` 下发，harness 解析端点并在同一接入方式内做容灾。服务端只有账号、市场与项目，没有档位、模型链、是否允许自带密钥这类配置。企业想统一"经济档走小模型、高级档走大模型"，只能逐台改配置或发版。

**差距**：云厂商与 Octop 一类平台通常由控制台下发模型策略与配额；任我行没有这层，多端一致性与成本治理靠人工。补这层不用重写调用链——harness 已有端点解析与容灾，只要把「档位 → 模型链」从本地常量换成服务端下发（PRD MDL-11）。

**影响**：换模型要发版或逐台改；没有统一成本策略；将来做硬配额时缺少服务端配置载体。

**实现方案**

1. 服务端增加档位配置：auto / 高级 / 基础 / 经济 → 模型链，附是否允许自带密钥与生效范围，按账号或组织下发。
2. 客户端登录后拉取并缓存档位表；离线、未登录或拉取失败回退 `models.json`，界面明确显示"当前使用本地模型配置"。
3. auto 由客户端按任务类型与上下文长度选档，结果写入任务元数据，任务详情可解释。
4. 协议不变：客户端仍直连模型端点；将来收口成服务端代理只替换 `base_url`（MDL-12），不改协议。
5. 档位表带版本号与签名，客户端只接受递增版本，拒绝回滚到旧策略。

**验收**

- 改服务端档位不需要发版，客户端下次拉取即生效。
- 离线时仍能用本地配置完成任务，并有中文提示。
- auto 的选择结果在任务详情可见。
- 旧版本档位表被客户端拒绝。

**依赖**：D-02；与 D-14 共用服务端配置载体。**工作量**：5–8 人日。**里程碑**：M3。

### D-30 自然语言定时任务覆盖有限（P3）

当前支持每小时、每天、每周、每月 1 日；明确拒绝"每 N 小时 / 分钟"与每月非 1 日，没有一次性日期任务，也没有 text / agent 任务类型区分。Octop cron 支持 cron 表达式、`interval:N`、`date:ISO8601` 与 text / agent 两类任务。方案：补一次性日期与间隔调度；解析结果先预览再确认；补示例与错误提示。验收：复杂表达先预览；一次性任务执行后自动停用；歧义有中文提示。工作量 2–3 人日。

### D-31 更多 IM 通道缺失（P3）

当前四个；Octop Gateway 10 个（含 Telegram、Discord、QQ、MQTT、微信 iLink 等），OpenHuman 14。方案：按客户需求逐个接入，优先 Telegram / Discord / 邮件；每接一个必须先过 D-04 的真实验收，不做"有代码即支持"；媒体、群策略与限流按 D-41 统一补，不在各通道里各写一套。工作量 5–8 人日/通道。

### D-32 设计模式组件库与令牌联动缺失（P3）

设计产物为单文件 HTML，未与设计令牌、组件库联动。方案：内置令牌与组件片段；产物可切换主题。工作量 8–12 人日。

### D-42 人格模板、专家共享与跨实例桥接缺失（P3）

**现状**：专家可自定义名称、头像、提示词与可用工具，协作风格只有四种预设；没有 MBTI 之类的人格模板库，没有专家共享 / 发布后的只读使用，也没有 Octop↔Octop 跨实例桥接；远程桌面仅本机只读（D-16）。

**差距**：Octop 有 16 种 MBTI 人格模板与测试，专家可分享 / 发布；Bridge 设计覆盖双向 WebSocket、HTTP 隧道、远程专家列表、附件与"历史权威在专家所在侧"，目前仍在实现中。任我行只有单机专家与账号侧项目协作，跨机器无法像本地专家一样对话。

**影响**：角色化能力靠用户手写提示词；团队无法共享专家；云端 / 家里 / 公司多实例场景只能各自维护。

**方案**：先做人格模板（提示词 + 行为风格，可克隆编辑）；再通过账号服务做只读专家共享（被分享者可对话、不可改配置，可撤销）；最后做跨实例桥接（双向 WS、鉴权、远程专家列表、对话转发，历史只存专家所在侧，附件落对端 inbound）。桥接需 TLS、连接级 scope、审计与重放保护。

**验收**：人格模板一键创建专家；共享专家只读可见，撤销后立即不可用；两个实例可与会话对端专家对话，历史只在对端可读；断网重连不重复消息。

**依赖**：D-02、D-23、D-19。**工作量**：10–15 人日。**里程碑**：M3。

## 附录 C 十维能力对照详表

> 口径：只把默认可用、能跑通的能力算"有"；Beta、路线图、未启用开关单独标注。Octop 事实来自其仓库 README、架构文档与 `octop-harness` / `octop-memory` / `octop-browser` / `octop-gateway` 文档；任我行事实来自当前源码。

### C.1 Agent

- **Octop**：单进程内由 `HarnessAgentManager` 管理多个 Agent；每个 Agent 组合模型、工具 / 技能、记忆后端与 LangGraph 检查点，工作区与记忆随 Agent 隔离；支持多 provider、HITL、子 Agent 与 ACP。
- **任我行**：普通任务默认走客户端内嵌 Rust harness；连接器、浏览器、电脑操作、知识库、专家套件、Hooks、审批、脱敏与 ACP 走 Python + AgentScope。专家是提示词 / 模型 / 技能白名单的注册表条目，不是独立运行时。
- **判断**：单 Agent 主链路可用，且 Rust 默认路径有冷启动优势；缺的是统一运行时抽象、每 Agent 独立工作区 / 检查点、可恢复 HITL 与线程内模型切换。
- **动作**：D-40；团队场景再叠加 D-34。

### C.2 AgentTeams

- **Octop**：`kind=team` 的主持人专家 + 普通成员专家；主持人只调度，异步 inbox 派工；同一成员串行、不同成员并行；成员回复带 `speaker_agent_id` 上群聊时间线；成员检查点 `主thread~成员id`、独立工作区；失败回叫主持人；停止只停主持人。当前为 Beta，在途任务用进程内 tracker，重启会丢。
- **任我行**：`engine/subagent_runtime.py` 是主任务内部的临时并发（最多 4 个、3 路并行、共享工作区、不可嵌套、结果汇总）；专家可配置角色与模型，但没有团队实体、房间、异步派工、成员独立检查点与失败回叫。
- **判断**：这不是"少一个 UI"，而是缺一套团队运行时与数据模型；现有子 Agent 只能算前置能力。
- **动作**：D-34；复用 D-40 的检查点，补团队在途任务表。

### C.3 Skills

- **Octop**：技能由 deepagents 技能中间件按 Agent 启停；共享技能 / 子 Agent 池已上线；自进化与插件市场仍是路线图；浏览器录制可生成 draft skill（独立 browser 文档有，主仓 README 仍列为待打磨）。
- **任我行**：Rust 侧 `SKILL.md` 目录 + 套件 + 签名市场；Python 平台层另有一套 YAML 技能（提示词、工具白名单、上下文、窗口），默认关闭。两套注册表语义不同，按专家重复安装，没有共享池、统一依赖检查或成功任务蒸馏。
- **判断**：单机技能可用，生态与复用不足；两套注册表是内部一致性问题，不是用户功能。
- **动作**：D-38；沙箱与更新分别见 D-08、D-07。

### C.4 MCP

- **Octop**：29 个内置连接器；remote / gateway / internal 三种模式；OAuth 一键授权；托管持久会话；工具按需加载；控制台可加自定义 MCP。
- **任我行**：stdio / streamable HTTP / SSE；OAuth PKCE、刷新、撤销；工具级 allowlist；探测与工具列表；没有 resources / prompts。Python 平台层有 Catalog 与客户端池，但默认关闭。市场可安装，配置仍要手填。
- **判断**：协议能力够用，差距在连接器目录、接入模式与授权体验；不是"缺 MCP 客户端"。
- **动作**：D-39；resources / prompts 归入 PRD MCP-08。

### C.5 Harness

- **Octop**：deepagents `create_deep_agent` + LangGraph + `AsyncSqliteSaver`；HITL 恢复；分层记忆中间件；子 Agent；持久 MCP；ACP；Local / S3 / COS / PostgreSQL 工作区；17 个 provider 预设；渐进式工具加载。
- **任我行**：Rust harness 有计划 / 工具审批、JSON 检查点、同签名工具跳过、`resumable`；Python 引擎有上下文压缩、MCP 工具懒加载与 PII 脱敏。Rust 路径没有压缩、图式 HITL、线程内切模型、按 Agent / 团队检查点或持久 MCP 会话。
- **判断**：短任务与中断续跑可用；长任务、审批恢复、模型切换与团队运行深度不足。这是 D-34 与 D-18 的共同底座。
- **动作**：D-40，验收并入 D-15、D-18。

### C.6 Gateway

- **Octop**：10 个平台；统一 `InboundMessage` / `MessageEvent` / `ContentPart`；`MediaBackend`；逐通道限流 / 超时 / typing；`push_text` / `push_content` / `push_to_all`；群 `visibility` / `activation`；同类型多实例按 `channel_id` 隔离。

- **判断**：数量与消息形态都落后；但真正的阻断是 D-04 的真实凭据验收，深度问题单列 D-41。

### C.7 Memory

### C.10 IM

- **Octop**：10 个平台；媒体与 `ContentPart`；群可见性 / 激活策略；限流 / 超时 / typing；主动推送；同类型多实例。

- **判断**：当前只能"文本演示"，不能"企业交付"；先拿真实租户，再补深度。
- **动作**：D-04 → D-41 → D-31。

### C.11 优先级结论

1. **先补底座**：D-40（harness 长任务与恢复）→ D-34（团队）→ D-35（记忆）。这三项决定"从个人工具到团队工具"是否成立。
2. **再补生态**：D-38（技能共享池）、D-39（连接器目录）、D-37（CLI）、D-36（浏览器录制回放）。它们提升复用与接入效率，但不阻断 0.2 交付。
3. **IM 单独走**：D-04 的真实租户验收是 P0；D-41 的媒体与群策略在真实验收之后做，避免在假服务端上堆功能。
4. **不要现在追**：D-42 的人格模板 / 专家共享 / 跨实例桥接属于 1.0 后生态；Octop 的 Bridge 本身仍在实现中，任我行没有必须抢先的压力。
