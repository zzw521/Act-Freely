## 0. 说明

### 0.1 本文收录什么

本文收录三类问题：

1. **交付阻断**：没有它就无法对外发布、部署或通过安全评审。
2. **产品缺口**：与 Octop、OpenHuman 对标后，用户会感知到的能力缺失。
3. **工程质量**：不直接面向用户，但会放大故障、拖慢迭代的问题。

不收录纯代码风格问题、无用户影响的重构、以及没有明确验收标准的主观优化。

### 0.2 缺陷分级

| 级别 | 判定标准 | 处理时限 |
| --- | --- | --- |
| P0 | 阻断发布、部署或安全评审；或存在数据 / 密钥 / 越权风险 | 0.2 前必须关闭 |
| P1 | 核心体验或商业闭环缺口；竞品已有且用户会直接比较 | 0.3 前关闭 |
| P2 | 竞争力与效率提升；有替代方案 | 1.0 前评估 |
| P3 | 长尾与打磨 | 按需 |

### 1.2 最关键的五个问题

1. **服务化部署没有闭环。** 引擎直跑与令牌链路已验证，但 Docker 镜像、反向代理、TLS、公网 SSE 都没有真实跑过。当前只能"本机演示"，不能"交付部署"。
2. **服务化没有用户体系。** 一个令牌等于全部权限，无法区分人、无法审计到人、无法做配额。这不是加个登录页能解决的，需要令牌到用户的映射与租户边界。
3. **操作系统级沙箱只覆盖 Windows。** Windows 版 AppContainer 隔离已落地并实测（终端、MCP stdio、ACP），macOS / Linux 与 Hooks 仍是策略沙箱，跨平台安全承诺还不能统一。
4. **IM 通道只对假服务端验证。** Slack、钉钉、企业微信、飞书四条链路都有代码，但没有真实企业应用凭据，线上行为未验收。
5. **跨平台未验证。** Windows 之外没有构建、随包 Python 与安装包验证，市场覆盖被限制在单一平台。

### 1.3 与竞品的差距结构

| 差距类型 | 代表项 | 性质 |
| --- | --- | --- |
| 平台能力 | 多租户、SSO、计费、管理后台 | 结构性，需版本级投入 |
| 集成广度 | IM 通道数、OAuth 集成数 | 可增量补齐 |
| 执行安全 | OS 沙箱、插件沙箱、审计防篡改 | 需专项 |
| 智能能力 | 向量检索、语音、工作流编排、上下文压缩 | 需选型与验证 |
| 工程效率 | 冷启动、内存、token 成本、可嵌入性 | 架构级，非短期可追平 |

## 3. P0 缺陷

### D-01 服务化部署链路未闭环

**现状**

- 引擎可以用 `--web-dir dist` 同端口托管静态前端与 `/api/*`，`/health` 与静态文件免令牌，`/api/*` 需令牌。
- 非回环绑定必须同时有 `TT_ALLOW_REMOTE_BIND=1` 与非空令牌。
- 仓库内有 `tongtian-tauri/deploy/Dockerfile` 与部署说明，但本机没有 Docker，镜像未构建、未运行。
- 真实 Nginx / Caddy 的 TLS、SSE 缓冲、超时、并发未验证。

**缺陷**

部署模板存在，但没有一条经过验证的"从零到可访问"路径。用户按文档操作可能遇到：镜像构建失败、反代缓冲导致 SSE 不流式、TLS 证书链错误、长连接被网关断开。

**影响**

- 无法对外承诺"可部署"。
- 服务化模式的 401 令牌弹窗、CLI 三命令都只在直跑场景验证过。

**实现方案**

1. 在 CI 或独立 Linux 主机上构建镜像，固定基础镜像与依赖版本。
2. 提供两套反代样例：Nginx 与 Caddy；显式关闭 `proxy_buffering`，设置 `proxy_read_timeout` 与 `X-Accel-Buffering: no`。
3. 用自签证书跑通 TLS，再验证公网域名。
4. 增加部署自检脚本：健康检查、静态页、带令牌 `/api/chat`、SSE 首包、断线重连。
5. 把"已验证 / 未验证"写进部署说明，未跑过的组合不得标为支持。

**依赖**：Docker 运行环境、一台 Linux 主机、可解析域名（公网验证）。

**验收**

- 干净主机执行文档步骤，15 分钟内得到可访问地址。
- SSE 首包 ≤ 2 秒，连续 10 分钟不被反代断开。
- 错误令牌返回 401，正确令牌可完成一次对话。
- 部署自检脚本全绿；失败时输出可定位的中文原因。

### D-02 服务化无用户体系，单令牌全权限

**状态**：最小版已落地（账号服务 JWT 声明与吊销、引擎侧 JWT 校验、按人审计与用量）；完整版（组织隔离、配额硬停、管理后台）未开始。

**现状（最小版改造前）**

- 服务化模式只有一个 `TT_ENGINE_TOKEN`，持有令牌即拥有全部能力。
- 没有用户、角色、租户、配额归属。
- 账号服务只服务桌面端登录，不参与引擎鉴权。

**缺陷**

单令牌无法回答"是谁在用""能用多少""出了事找谁"。这会让服务化模式停留在个人试用，无法进入团队或企业。

**影响**

- 无法做按人配额、审计到人、权限分级。
- 令牌泄露等于全部数据与执行能力泄露。
- 无法支持多团队隔离。

**实现方案（最小版，M1）**

1. 引擎接受账号服务签发的短期 JWT，校验签名、过期、受众。
2. 令牌声明包含 `sub`（用户）、`org`（组织）、`role`、`quota`。
3. 每次请求把 `sub` 写入审计与用量；未知用户拒绝。
4. 保留静态令牌作为单机兼容模式，但启动时明示"无用户隔离"。

**完整版（M3）**

1. 组织 / 成员 / 角色模型；邀请与移除。
2. 租户级数据隔离：工作区、会话、知识库按 `org` 分区。
3. 配额与预算按组织 / 用户两级；超限硬停。
4. 管理后台：成员、配额、模型、审计。

**依赖**：账号服务扩展、数据库迁移（增量）、管理后台。

**进展（2026-10-28）**：账号服务（`tongtian-server`）已完成最小版 JWT 声明与吊销能力——access/refresh 令牌携带 `iss`/`aud`/`sid`/`org`/`quota`；access 令牌绑定 `sessions.id`，退出、刷新轮换或管理员强制下线后立即失效；新增管理员接口 `PATCH /api/v1/admin/users/{uid}`（设置组织与配额，返回 `sessionsRevoked`）与 `POST /api/v1/admin/users/{uid}/revoke-sessions`；`users` 表通过增量迁移增加 `org_id`/`quota_json`。引擎侧（`tongtian-tauri/engine`）已接入同一套 JWT：校验 HS256 签名、`exp`、`iss`、`aud`、`type=access`、`sub`、`sid`，支持 `TT_ENGINE_ALLOWED_USERS` 白名单；每个 `/api/*` 请求记录 `sub/org/role/sid/方法/路径/状态/耗时/IP`，`GET /api/audit` 可查（普通用户仅自己、管理员全部），可选用 `TT_ENGINE_AUDIT_LOG` 追加 JSONL；模型用量台账按 `sub` 归集，`/api/usage` 与 `/api/usage/report` 支持按用户过滤并返回 `users` 汇总。静态 `TT_ENGINE_TOKEN` 保留为应急通道，非回环绑定允许“静态令牌或 JWT 密钥”二选一。服务端与引擎自测覆盖签发字段、`aud`/`iss`/`type`/`sid` 反例、白名单、审计隔离与落盘、用量归属、绑定准入。**仍未完成**：组织级数据隔离（工作区、会话、产物按 `org` 分区）、配额硬停、账号侧吊销的实时内省（引擎只按 `exp` 失效，最长 15 分钟），因此“两个用户互相看不到对方会话与产物”的验收项尚未满足。

**验收**

- 两个用户使用同一引擎，互相看不到对方会话与产物。**未满足**：引擎尚未按 `org` 分区，审计与用量的可见范围收窄不等于数据隔离。
- 审计可按用户筛选；用量可按用户聚合。**已满足**（引擎自测覆盖普通用户只看自己、管理员看全部、用量按 `sub` 汇总）。
- 删除用户后其令牌立即失效。**部分满足**：账号服务侧签发即绑定 `sessions.id`，吊销即时生效；引擎不内省账号服务，只按 `exp` 失效，最长 15 分钟窗口。
- 超配额请求返回明确错误码，不执行任务。**未满足**：配额目前只是令牌声明与展示值，引擎未做硬停。

### D-03 无操作系统级沙箱

**状态**：进行中。Windows 版已落地并通过实机验收；macOS / Linux、Hooks 与写暂存审批未完成。

**现状**

- 两层隔离同时存在：
  - 策略沙箱：工作目录边界、工具白名单 / 黑名单、L0 只读 / L1 / L2 执行等级、路径黑名单，在工具调用点拦截并把中文原因回给模型、写审计。
  - 系统隔离（Windows 10/11 AppContainer）：终端会话、MCP stdio 服务、ACP 外部 Agent 的真实子进程以容器令牌启动，越界写入与读取数据根密钥由系统 ACL 拒绝。
- 启动方式是主程序的隐藏子命令 `--tt-sandbox-run`：单二进制、不进 WebView、在 Tauri 初始化前返回，避免 sidecar 的打包与签名分叉。
- 配置落 `security_policies.system_sandbox`；启用时真实创建 profile，创建失败就拒绝启用，不保存一份永远不生效的"已开启"。
- 安全设置页把两层分开标注：策略沙箱按工作区展示 L0/L1/L2，系统隔离展示请求 / 平台支持 / 实际生效三栏与未生效原因。

**已实现要点**

- 容器 profile 固定为 `TongTian.Agent`，同一台机器复用，不每次启动重建。
- 工作区授予读写，沙箱临时目录可写；会话库 `tongtian.db`（含 `-wal` / `-shm`）、配额台账、审计导出目录、意识目录 `TONGTIANWORK_HOME` 显式拒绝。
- 环境块过滤：名字含 token / secret / password / api_key / access_key 的变量不进入沙箱；连接器显式配置的变量名通过 `--allow-env` 保留。
- 网络能力整体授予：关闭时能力数为 0，开启时授予 internetClient 组。
- 子进程挂 Job Object（`KILL_ON_JOB_CLOSE`），父进程退出即回收整棵进程树。
- ACL 授予带缓存（`%LOCALAPPDATA%\TongTianSandbox\<profile>\grants.txt`），同一路径只传播一次；`TT_SANDBOX_NO_CACHE=1` 可强制重做。
- 引擎侧 `engine/sandbox_launcher.py` 统一套壳；配置了隔离却找不到启动器时一律拒绝执行，不静默降级。

**未完成**

- macOS / Linux 的系统级隔离（见 D-05）。
- Hooks 命令仍以应用权限执行：它们是用户逐条放行的本机自动化，且逐文件授权大目录的成本不可接受。
- 文件写入先落暂存区、审批后合并与 diff 预览。
- 按进程 / 工具的出域域名白名单，目前只有整组开关。
- 包管理器启动的 MCP 服务需要补充可读目录，界面上还没有引导。

**实现方案（剩余）**

1. macOS 用 seatbelt、Linux 用 bubblewrap 实现与 Windows 同协议的启动器，主程序按平台分发。
2. Hooks 纳入隔离：先解析出脚本路径，只对脚本所在目录授予只读，避免整树传播。
3. 写操作走暂存区 + diff 审批，与现有工具审批网关合并。
4. 出域白名单下沉到系统隔离层，与策略沙箱的域名清单共用一份配置。

**验收**

| 验收项 | 结果 |
| --- | --- |
| 越界写文件被系统层拒绝 | 通过：工作区外写入 `PermissionError`，文件未生成 |
| 子进程无法读取数据根中的密钥文件 | 通过：读取临时数据根内的会话库与密钥文件 `PermissionError` |
| 关闭网络后无法访问外网 | 通过：公网连接报 `WinError 10013`；开启后公网可达 |
| 安全设置页显示真实等级 | 通过：桌面版实机点开关，请求 / 生效 / 未生效原因随真实状态变化；关闭后回读配置为 `false`；平台不支持或未启用时对应开关禁用 |

自动化覆盖：

- `src-tauri/tests/sandbox_acceptance.rs`：真实进程验收越界写、密钥读取与断网。
- `tests/integration/engine_sandbox_wrapper_selftest.py`：套壳命令行结构、启动器缺失时拒绝执行、终端接入。
- `cargo test --lib sandbox::`：参数解析、环境块过滤、敏感路径、状态计算。
- `tests/unit/security/sandbox-system-contract.test.ts`：设置通道按对象透传（关闭必须落 `false`）、启用前先建 profile、启动恢复、设置页三栏与禁用条件。

**已知边界**

- AppContainer 的网络隔离包含回环与局域网：即使开启出网，容器内进程仍连不上 `127.0.0.1` 与局域网地址，需要管理员配置 loopback exemption。沙箱内的终端访问本机服务会失败。
- 首次给大目录授予工作区权限要逐文件传播 ACL，耗时与文件数成正比；之后走缓存。浏览器预览环境不提供系统隔离，设置页如实显示不支持。
- 系统隔离只对新启动的引擎进程生效，改完设置需要重新开始任务。

### D-04 IM 四通道仅假服务端验证

**现状**

- Slack、钉钉、企业微信、飞书四个通道均有实现，包含长连接、消息收发、会话映射。
- 测试使用本机假服务端（`fake_slack.py` / `fake_dingtalk.py` / `fake_wecom.py` / `fake_feishu.py`），验证握手、回执、消息循环与回贴。
- 没有真实企业应用凭据，未验证平台审核、权限范围、频率限制、消息格式差异。

**缺陷**

"支持四个 IM 通道"目前是代码事实，不是产品事实。真实环境可能出现：应用审核不通过、事件订阅配置错误、消息卡片格式不兼容、长连接被平台限流。

**影响**

- 企业交付时无法承诺开箱即用。
- 出问题后缺少平台侧排查经验。

**实现方案**

1. 为每个通道建立真实测试租户，至少完成一个通道的端到端验收。
2. 记录每个通道的：应用类型、权限范围、事件订阅、回调 / 长连接配置、消息格式限制。
3. 增加通道健康检查：凭据有效性、连接状态、最近一次收发时间。
4. 对未验证通道在界面上标注"未验证"，不显示"已支持"。
5. 把假服务端测试保留为回归测试，但不能替代真实验收。

**依赖**：四个平台的企业应用管理权限、审核周期、测试群。

**验收**

- 至少一个通道在真实企业租户中完成"发消息 → Agent 执行 → 回贴结果"。
- 断线后自动重连，重连期间不丢消息。
- 凭据错误、权限不足、频率限制都有中文提示。
- 其余通道明确标注验证状态。

---

### D-05 macOS / Linux 未验证

**现状**

- 开发与验证集中在 Windows 10/11 + WebView2。
- 随包 Python 脚本只处理 Windows embeddable amd64。
- macOS / Linux 的构建、钥匙串、系统权限、安装包、通知与角标均未验证。

**缺陷**

跨平台是桌面产品的基本预期；当前只有 Windows 可用，且没有证据说明其他平台会在何时可用。

**影响**

- 市场覆盖被限制在单一平台。
- 企业客户中 macOS 占比较高时无法交付。

**实现方案**

1. 先做"可构建"：CI 增加 macOS / Linux 构建任务，修复编译与打包错误。
2. 再做"可运行"：Python 运行时按平台准备；钥匙串适配；系统权限入口适配。
3. 最后做"可验收"：每个平台跑核心链路（登录、对话、产物、执行面）。
4. 明确平台能力矩阵：哪些执行面仅 Windows，哪些跨平台。

**依赖**：macOS / Linux 构建机、代码签名证书（分发）、平台测试设备。

**验收**

- 两个平台均能构建出安装包并启动。
- 核心链路在各自平台通过。
- 平台差异在文档与界面中明示。

## 4. P1 缺陷

### D-06 协作无实时推送，10 秒轮询

**现状**：协作页每 10 秒拉取一次项目与任务；成员变更、评论、结果回报都有延迟。

**影响**：多人同时操作时看到旧状态；评论像"留言板"而不是协作。

**方案**：账号服务增加 SSE 或 WebSocket 通道；客户端订阅项目事件；断线重连并按游标补拉。保留轮询作为降级。

**验收**：两人同时操作，状态在 1 秒内同步；断网恢复后不丢事件。

**进展（2026-10-28）**：服务端已增加 `GET /api/v1/projects/{id}/events`（按 `since` 增量拉取）与 `GET /api/v1/projects/{id}/events/stream`（SSE，500ms 轮询、15 秒心跳、支持 `Last-Event-ID` 续传、成员被移除时关闭）。服务端测试已覆盖游标、权限与实时推送；桌面端仍是 10 秒轮询，待接入订阅。

**工作量**：2–3 人日。

---

### D-07 市场只安装不更新、无撤销

**现状**：客户端只有安装命令；服务端有版本与更新时间，但没有客户端更新检查，也没有撤销 / 下架列表。

**影响**：已安装的恶意或有缺陷版本无法远程止损；用户长期停留在旧版本。

**方案**：安装记录版本与哈希；启动或手动检查更新；支持"固定版本"；服务端增加撤销列表，客户端命中后禁用并提示卸载。

**进展（2026-10-28）**：服务端已增加管理员版本撤销 / 恢复接口（`POST /api/v1/admin/items/{type}/{id}/versions/{version}/revoke|unrevoke`）与公开下架列表 `GET /api/v1/revoked`；撤销版本从"最新版本"计算中排除，下载与 MCP 配置接口返回 `410 ITEM_REVOKED`，撤销字段以增量迁移写入 `item_versions`。服务端测试覆盖权限、幂等、最新版本回落与恢复；客户端安装记录、更新检查与撤销禁用尚未接入。

**验收**：发布新版本后客户端可检测并升级；撤销后已安装包被禁用且不可执行。

**工作量**：1–1.5 人日。

---

### D-08 插件 / 套件无代码执行沙箱

**现状**：插件模块只做 `plugin.json` 校验与模板生成；套件只消费 `commands` 与包内 `SKILL.md`；`mcpServers` / `hooks` / `agents` 等字段被忽略并列出。

**影响**：无法支持真正的插件生态；一旦开放代码执行，现有边界不足以保证安全。

**方案**：定义插件能力清单（命令、技能、MCP、Hook）；默认只允许声明式能力；代码执行走独立进程 + 权限清单 + 资源上限；安装时展示将获得的权限。

**验收**：插件无法访问未声明路径与网络；超资源被终止；卸载清理干净。

**工作量**：8–12 人日。

---

### D-09 知识库仅词法检索

**现状**：SQLite FTS5 + 中文单字 / 二元组 + 英文词元；无 embedding、无 rerank、无 OCR；PDF 只提取可读文本。

**影响**：同义表达召回差；扫描件无法检索；长文档片段排序不稳定。

**方案**：保留 FTS5 作为兜底；增加可选向量索引（本地 embedding 模型或云端）；增加 rerank；扫描件走 OCR 或明确提示"未提取到文本"。

**验收**：同义查询命中率相对基线提升；无向量模型时自动降级且提示；扫描件有明确状态。

**工作量**：10–15 人日。

---

### D-10 无可视化工作流编排

**现状**：只有单任务 cron；无节点编排、条件分支、人工审批节点、失败重试策略。

**影响**：复杂重复任务只能写成长提示词，不可复用、不可观测。

**方案**：先做线性步骤 + 条件分支 + 审批节点；再考虑画布。工作流定义可版本化、可导入导出。

**验收**：一个包含"抓取 → 摘要 → 审批 → 生成文档"的工作流可保存、复用、查看每次运行。

**工作量**：15–20 人日。

---

### D-11 无语音输入与实时语音

**现状**：设置中有"语音输入"入口，标注"尚未提供"；无 ASR、无 TTS、无实时语音会话。

**影响**：移动与免手操作场景缺失；与 OpenHuman 的差距明显。

**方案**：先做按住说话转文字（系统或云端 ASR）；再做回复朗读；实时语音作为独立项目评估。

**验收**：语音输入可插入输入框；失败有原因；隐私模式下不上传音频。

**工作量**：10–20 人日。

---

### D-12 无自动更新渠道

**现状**：设置页如实显示"未配置更新渠道"，更新方式为覆盖安装。

**影响**：安全修复无法及时触达；用户版本碎片化。

**方案**：接入 Tauri updater 或自建更新清单；签名校验；灰度与回滚；离线环境支持手动包。

**验收**：新版本可检测、下载、校验、安装；失败可回滚；无更新渠道时界面不放假按钮。

**工作量**：5–8 人日。

---

### D-13 应用快照与浏览器上下文接力缺失

**现状**：应用快照入口存在但明确"尚未提供"；浏览器会话不共享用户登录态与标签页上下文。

**影响**：用户需要手工复制粘贴上下文；浏览器任务从零开始。

**方案**：应用快照先做"用户主动触发 + 预览 + 确认后上送"；浏览器接力先做受控会话内的标签页与登录态复用，明确隔离边界。

**验收**：快照内容上送前可见可取消；浏览器任务可复用已授权会话；机密级内容不上送。

**工作量**：2–3 人日（快照）+ 后续浏览器接力单列。

---

### D-14 配额 / 预算无 UI 与告警

**现状**：Rust 侧有配额门与档位跃迁事件，运行中可因预算耗尽转 `budget_paused`；前端没有配置入口与可视化。

**影响**：用户不知道为什么任务被暂停；无法提前设置预算。

**方案**：设置页增加任务 / 日 / 月预算；用量页显示当前档位与剩余；达到阈值发通知；超限说明原因与恢复方式。

**验收**：预算可配置并生效；暂停有中文原因；调整后无需重启。

**工作量**：0.5–1 人日。

---

### D-15 失败步骤不能单步重试

**现状**：失败后可重新生成整轮，不能只重试失败步骤；长任务返工成本高。

**影响**：一次工具超时导致前面所有步骤重跑，浪费 token 与时间。

**方案**：为每个步骤保留输入与工具结果；支持"重试此步"与"从此步继续"；幂等工具直接重放，非幂等工具要求确认。

**验收**：单步失败后可只重试该步；已完成步骤不重复执行；非幂等操作有确认。

**工作量**：3–5 人日。

---

### D-16 远程桌面仅本机只读

**现状**：当前实现是"本机桌面 → 当前窗口"的受控实时画面；单次最长 10 分钟，帧间隔不小于 700ms；不提供键鼠注入；仅 Windows。

**影响**：产品名容易被理解为"远程控制另一台电脑"，实际能力差距大。

**方案**：短期在界面与文档中改称"本机画面查看"；中期若要做真正远程桌面，需要中继服务、主机配对、端到端加密与输入通道，单独立项。

**验收**：命名与实际能力一致；若做远程控制，必须有配对、加密、授权与审计。

**工作量**：改名 0.5 人日；真正远程 10–15 人日以上。

---

### D-17 ACP / 终端高级集成未真实验收

**现状**：终端自测覆盖真实 shell 会话、令牌校验、AI 只给建议不执行；ACP 服务端与客户端有自测，但部分环节使用本机脚本化对端。

**影响**：与真实编辑器 / IDE 的互操作未证明。

**方案**：选一个真实 ACP 客户端做端到端；记录协议版本与能力差异；不支持的请求明确报错。

**验收**：真实客户端可完成一次会话与工具调用；不支持项有明确错误。

**工作量**：5–8 人日。

---

### D-18 性能与 token 效率落后

**现状**：普通任务由客户端内嵌 Rust harness 执行，连接器、浏览器、电脑操作、知识库、专家套件、Hooks、工具审批、出站脱敏与 ACP 仍交给 Python + AgentScope 引擎；两条链路都有上下文预算与工具结果截断，但没有公开的冷启动、内存、token 对比数据。OpenHuman 公开宣称单进程 Rust、68MB 峰值、2.6 倍更少 token。

**影响**：成本与响应速度处于劣势；大规模部署时资源开销高。

**方案**：先建立可复现的基准（冷启动、首包、单任务 token、峰值内存）；再做低风险优化：引擎预热、工具结果截断与摘要、系统提示精简、按任务裁剪工具集；架构级替换需单独评估。

**验收**：基准可重复；优化后单任务 token 与首包时延有可量化下降；不牺牲产物质量。

**工作量**：15–25 人日。

---

### D-19 无可嵌入 SDK / 服务端 API

**现状**：引擎有 HTTP + SSE，但没有面向第三方的稳定 API 契约、SDK、鉴权与配额；服务化模式仍是单令牌。

**影响**：无法被其他产品集成；失去 Octop / OpenHuman 的服务端场景。

**方案**：先稳定 `/api/chat` 与事件契约；提供 OpenAPI 文档与最小 SDK；鉴权依赖 D-02；增加速率限制与幂等键。

**验收**：第三方按文档可在一天内完成一次对话集成；契约变更走版本化。

**工作量**：15–25 人日。

---

### D-20 跨进程错误处理不统一

**现状**：渲染层仍有 15 处 `instanceof Error` 判断；Tauri command 的 `Err(String)` 到 JS 不是 `Error` 实例，导致部分分支拿不到错误信息。

**影响**：错误提示退化为"未知错误"；排查困难；用户看到英文裸字符串。

**方案**：统一错误封装：Rust 返回结构化错误码 + 消息；前端统一 `errorTextOf`；禁止新增 `instanceof Error`；补充测试覆盖。

**验收**：所有命令失败都能显示中文原因；错误码可检索；无裸字符串透出。

**工作量**：3–5 人日。

---

### D-21 真实外部链路测试不足

**现状**：84 个前端测试文件、Rust 单元测试、服务端测试、引擎自测脚本；客户端 harness 用本地假模型服务覆盖了规划、工具调用、取消与检查点，但没有真实模型、真实 IM、真实反代、跨平台链路的自动化验证。

**影响**：回归发现晚；"本地全绿"不等于"线上可用"。

**方案**：建立分层测试：单元 / 契约 / 集成 / 真实环境冒烟；真实环境测试用独立租户与预算上限；失败不阻塞开发但阻塞发布。

**验收**：发布前真实环境冒烟清单全部执行；失败有记录与负责人。

**工作量**：10–15 人日。

---

### D-22 文档、版本与入口不一致

**现状**：产品曾用名"通天办公"仍出现在部分模块与注释；README 写"三种工作模式"，代码定义四种、默认启用三种；部分入口已重定向但文档仍按旧路径描述。

**影响**：用户与开发者认知偏差；支持成本上升。

**方案**：统一产品名与版本口径；入口以路由表为准；模式描述写"默认三种，写作可选"；每次发版检查文档链接与截图。

**验收**：仓库内无过期入口描述；README、PRD、界面三处口径一致。

**工作量**：2–3 人日。

---

### D-33 XLSX / DOCX 真实产物未实现

**现状**

- 引擎的真实生成器只有：设计模式的单文件 HTML、幻灯片模式的 `.pptx`（python-pptx）、写作模式的 Markdown。
- 没有 OpenXML 表格 / 文档生成工具，也没有 `openpyxl` 或 `python-docx` 依赖。
- 旧 README 与部分规格把 `.xlsx` 看板、`.docx` 报告列为已有产物，属于过度表述。

**影响**

- 用户按"办公产物"预期索取表格或 Word 文档时，只能拿到 Markdown / CSV，或一个改名的假文件。
- 产物导向的核心卖点被削弱。

**实现方案**

1. 增加 `generate_xlsx`：工作表、表头、列宽、数字格式、基础公式、多 sheet。
2. 增加 `generate_docx`：标题层级、段落、列表、表格、页眉页脚、中文字体。
3. 两种工具都走真实 OpenXML 库，缺失依赖时如实报"未安装"，禁止改名冒充。
4. 产物预览复用现有文件预览；不能预览时提供外部打开。
5. 在模式说明与 README 中按实际能力描述，未实现前不得列为已有产物。

**依赖**：`openpyxl` / `python-docx`（或等价库）、随包 Python 依赖表更新、预览组件适配。

**验收**

- 生成的文件可被 Office / WPS 正常打开，扩展名与内容一致。
- 中文、数字格式、表格样式在生成文件中可见。
- 依赖缺失时返回明确错误，不生成假文件。
- README、PRD、界面三处描述一致。

**工作量**：8–12 人日。

## 5. P2 / P3 缺陷

### D-23 多账号与组织 / SSO（P2）

当前单账号；无组织、无 SSO、无 SCIM。方案：账号服务增加组织模型，桌面端支持切换账号；SSO 先做 OIDC。工作量 10–15 人日。

### D-24 移动端缺失（P2）

无 iOS / Android 客户端，也无移动端只读视图。方案：先做 Web 响应式只读 + 通知；再评估原生。工作量 20–30 人日。

### D-25 无障碍与主题不完整（P2）

基础键盘可用，但未做 WCAG 审计；主题只有设计令牌，无完整深浅色与密度切换。方案：键盘路径、焦点可见、对比度、读屏标签逐项验收。工作量 5–8 人日。

### D-26 产物版本历史与回滚缺失（P2）

产物覆盖写入，无版本。方案：每次生成保留版本与 diff；可回滚；配额清理旧版本。工作量 5–8 人日。

### D-27 审计防篡改与合规报告缺失（P2）

审计为本地追加文件，可被本机用户修改；无合规报告导出。方案：哈希链 + 可选远端归档；合规模板导出。工作量 8–12 人日。

### D-28 无遥测与崩溃上报（P2）

线上问题不可见。方案：默认关闭、显式同意、可查看将发送的内容；崩溃本地留存并提示导出。工作量 3–5 人日。

### D-29 Docker / SSH 远程工作区缺失（P2）

仅本地目录。方案：工作区后端抽象；Docker 与 SSH 执行器；凭据进钥匙串；资源与网络限制。工作量 10–15 人日。

### D-30 自然语言定时任务覆盖有限（P3）

常见表达可用，复杂表达歧义。方案：解析结果先预览再确认；补充示例与错误提示。工作量 2–3 人日。

### D-31 更多 IM 通道缺失（P3）

当前四个；Octop 8+、OpenHuman 14。方案：按客户需求逐个接入，优先 Telegram / Discord / 邮件。工作量 5–8 人日/通道。

### D-32 设计模式组件库与令牌联动缺失（P3）

设计产物为单文件 HTML，未与设计令牌、组件库联动。方案：内置令牌与组件片段；产物可切换主题。工作量 8–12 人日。

## 9. 风险

| 风险 | 概率 | 影响 | 应对 |
| --- | --- | --- | --- |
| Docker / 反代验证被环境阻塞 | 中 | D-01 延期 | 提前准备主机与域名；先用本地 Linux VM |

| 多租户改造触及数据模型 | 高 | D-02 延期 | 先做 JWT 映射，再做分区迁移 |
| 性能优化收益不及预期 | 中 | D-18 无效 | 先建基准，再决定是否投入架构替换 |
| 插件沙箱开放后出现恶意包 | 中 | 安全事件 | 默认声明式；代码执行需审核与资源上限 |
| 跨平台维护成本被低估 | 中 | 长期负担 | 平台能力矩阵；Windows 优先 |
