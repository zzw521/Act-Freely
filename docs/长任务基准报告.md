# 长任务基准报告（D-40 第 6 项）

日期：2026-11-03。被测对象：客户端内嵌 Rust harness 与 Python + AgentScope 引擎。
本报告只描述这两次实测跑出来的数字与它们的口径，不代表任何真实模型的成本或延迟。

## 1. 这轮基准回答什么问题

D-40 第 6 项要求「建立长任务基准（100 轮、30 个工具、审批中断），记录 token、首包与恢复耗时」。
两条链路跑同一个假端点、同一套脚本轮次、同一条 token 折算公式，产出两份可对读的 JSON：

- Rust harness：`tongtian-tauri/src-tauri/src/harness/runner.rs` 里的 `bench_long_task_100_rounds`，打印 `BENCH_JSON {...}`。
- 引擎：`tongtian-tauri/tests/integration/engine_long_task_bench.py`，打印 `ENGINE_BENCH_JSON {...}`。

两边都是 4 段 × 每段 25 轮工具 + 1 次正文收尾 = 104 次任务模型调用、100 次真实写盘，
外加压缩带来的 4 次摘要调用；段与段之间携带历史，模拟一个跨越多次输入的长任务。

## 2. 口径（读数字前必读）

1. **端点是本机假服务**，不联网、不消耗真实 token。`prompt_tokens` = 实际请求体字节 ÷ 4 向上取整，
   completion 固定回报 40/次。两侧连的是同一个端点、用的是同一条公式，所以**可比**；
   绝对值不是真实分词，不能拿去和竞品比成本。
2. **首包** = 客户端从发出请求到解析出第一个「有内容」增量的时间。假端点分三段写：
   只发响应头 → 隔 40ms 发第一个内容包 → 隔 25ms 发 usage 与结束标记。
   所以首包的理论下界就是 40ms，多出来的部分是各链路自己的开销；只带 usage 的收尾包不算首包。
   **整包** = 同一次调用到流结束的时间，下界 65ms。
3. **压缩的判据两侧不同**：引擎用 tiktoken 精算（中文约 1 字 1 token，高于字节 ÷ 4），
   harness 优先用端点回报的折算数。因此「压缩在第几轮触发」两侧本来就不完全同，
   报告只比压缩次数与压缩后的体量，不比对触发轮次。
4. **「30 个工具」按设置页同口径实现为单轮工具循环上限 30**（`runtime.agentPolicy.maxIters`），
   整场共 100 次工具调用。两侧实际下发的工具清单数量不同（引擎注册得更全），
   这本身就是 prompt 体量差的一部分，没有抹平。D-40 验收里那句「30 个 MCP 工具只加载被检索到的 schema」
   属于第 5 项，本轮**没有**覆盖。
5. **中断方式两侧不同**：harness 停在工具审批确认框上（真实 HITL 形状，待审批工具欠着）；
   引擎用「工具执行后模型链路连续 500」触发，因为引擎的逐工具审批要连本机审批网关，
   基准不带网关跑。两边最后都落成同一形状的检查点：已完成的工具不重放、欠着的补完。
6. **恢复耗数的范围不同**：harness 的 `restore_ms` 是同进程内「从检查点接回待审批回合」的时间；
   引擎的 `restore_ms` 是调用 `/api/chat/review` 走完整个恢复（重建 Agent、装工具、灌记忆、
   再打一次模型、执行工具）的时间。两个数不该直接相减当成「快 36 倍」。
7. **运行环境**：工作目录、会话目录、检查点目录全部指向临时目录；隐私模式关闭（要量的就是落盘开销）；
   文件档位显式 `auto_approve`，绝不弹系统确认框；不写意识记忆。
8. **引擎侧多跑了一个不计量的暖场任务**：openai/httpx 客户端的第一条请求含建冷启动的固定开销，
   会把首包读数倒挂成「小上下文比大上下文慢」。harness 每次调用都新建客户端，没有这个台阶，
   所以只在引擎侧剔除第一笔，并在 JSON 的 `caliber.warmUp` 里写明。
9. **表里的数字是各跑一次录下的**，同机复跑会有浮动：2026-11-03 同日复测引擎侧，墙钟 17,677 → 18,736 ms、
   满上下文首包 avg 50 → 52 ms、整包 76 → 77 ms、每轮间隔 max 426 → 440 ms、续跑 506 → 546 ms。
   确定值只有这些：模型调用 104 / 写盘 100 / 摘要 4、产物 100 个文件、请求体总量 7,183,371 B、
   折算 prompt 1,795,843（峰值 32,244）、压缩 4 次、携带消息 24 条——同配置复测一字不差；
   带时间戳的落盘体量与所有毫秒读数都会动（检查点大小 30,426 → 30,439 B 就是这么来的）。
   引用本表按「量级 + 口径」理解，不要拿单个毫秒数下结论。

## 4. 中断与续跑

| | Rust harness | Python 引擎 |
| --- | --- | --- |
| 中断触发 | 工具审批挂起（待审批 2 个工具） | 工具执行后模型链路连续 500（端点侧 3 次被拒，含 SDK 重试） |
| 中断时检查点写盘 | 1 ms | 1,946 ms 为整段中断任务的墙钟，检查点单次写盘 1 ms |
| 恢复耗时 | 14 ms（同进程接回待审批回合） | 506 ms（`/api/chat/review` 全链路重建 + 续跑） |
| 续跑用掉的模型调用 | 1（续跑那一轮） | 2 |
| 已完成工具是否重放 | 否，同签名跳过 | 否，`skippedDuplicates = 1` |
| 证据 | 待审批工具被补齐、已完成的没再执行 | 续跑重发同一条写盘参数被中间件挡下，人工改动没被覆盖 |

引擎这一侧的续跑证据链是实的：中断前最后一次成功写盘的那个文件被人为改成
「中断后有人改过，续跑不许覆盖」，续跑结束后它仍是这句话，而且检查点里 `skippedDuplicates` 从 0 变成 1。
（早先版本用目录里排序最后一个文件当探针，`k10` 会排在 `k2` 前面，探针探错文件这条证据就废了，已改成记端点
实际发出的那条写盘参数。）

## 5. 这轮基准顺手挖出来的三件事

1. **引擎的上下文压缩会静默失败**（已修）。第一版全量基准里，引擎压缩触发了 36 次、成功 0 次：
   AgentScope 要求模型按结构化协议回摘要，端点回纯文本时它只打一条 WARNING 就继续跑，
   上下文从 30,019 一路涨到 47,086（tiktoken）——既超过它自己配的 32,768 窗口，也说明
   「压缩」在这条路上等于零收益，还每轮白烧一次摘要调用。修法是模型包装层记下
   「这一轮结构化输出到底有没有拿到 metadata」，压缩失败就转成用户看得见的 `ctx-compress-error`
   并关掉本次任务的重试；引擎自检补了三条断言。修完之后压缩次数从 36 次失败变成 4 次成功，
   请求体总量从 15.7 MB 降到 7.18 MB，墙钟从 26.7 s 降到 17.7 s，单次峰值从 49,438 折算 tokens
   回落到 32,244。假端点从不拒绝超限请求，换成真 32k 模型时这一条会直接报错，不是「慢一点」。
2. **每轮固定预处理这一项 Rust 反而更贵**（2.9 ms vs 0.18 ms）。原因是两边的活不同：
   harness 每轮要把消息深拷贝进请求体再 serde 序列化，Python 侧传引用给 `json.dumps` 就完事。
   这不是「序列化语言差异」，是构建请求体那一笔拷贝的账，报告按各自实际发生的工作列，不折成一条。
3. **自检重复跑会假失败**（已修）。引擎用量台账是落盘重放的，SSE 自检里「calls == 1」这类断言
   在第二遍跑时会在上一遍的数字上继续累加。现在自检把台账换成临时文件，连跑两遍都绿。

## 6. 还没覆盖的

- 真实模型、真实网络、真实单价：一个都没碰，所有绝对值都是折算口径。
- 30 个 MCP 工具只加载被检索到的 schema（D-40 第 5 项）：本轮未验。
- 团队成员的独立检查点：harness 的检查点分层已经按执行体分好目录（负责人 / 各专家 / 各成员），
  成员入口就位，但**两条链路都还没有真的成员运行时**——引擎的子 Agent 不落检查点，
  `spawn_subagents` 在父台账里只是带副作用的工具。这块要等 D-34。
- 长时间跨进程重启的真实演练（杀进程再拉起来）：本轮只在同进程内验证了检查点读写与续跑语义。

```bash
# 引擎用量采集与压缩协议自检

# 注入面瘦身前后对照（§8，D-18 / 卡 #155）：两档注入负载 × A/B 上限开关，四跑

  BENCH_INJECTION=$prof BENCH_CAPS=$caps \

```

`BENCH_CAPS=off` 把上面四个常量在**基准侧**推到 `10**9 / 0`（组装段读模块全局，运行时立即生效），

`BENCH_INJECTION=none` 才是 2026-11-03 那版的裸提问口径，所以本表数字**不能**和 §3 那两列互比——
本表两侧都带同一份注入负载，比的只是上限开不开。

### 8.4 读数字时必须一起看的四件事

1. **压缩空转**：改动前 heavy 档 104 次任务调用配了 **103 次摘要调用**——固定注入本身就把
   单次请求顶到接近/超过配置的上下文窗口（折算峰值 38,055，窗口配的 32,768；注意这是
   §2 第 1 条的字节 ÷ 4 折算口径，引擎自己的压缩判据走 tiktoken，两者不完全同，
   但「摘要调用 103 次」这个计数量是端点数出来的，不依赖折算口径）。于是每一轮都触发压缩、
   每一轮压缩都只带回来一点点余量（固定注入那部分压不掉），下一轮又超。这 82 次多余调用是净烧钱。
   上限生效后摘要调用降到 21 次，且「压缩真的取到了结构化摘要」这条断言在四跑里都过
   （量的就是真压缩，不是每次都失败的假压缩）。
2. **每千 tokens 墙钟这个指标会反向**：分子是链路自己的开销（已减掉假端点每次请求自己
   sleep 的 40＋25 ms），它按**调用次数**走、不按体量走。注入变少 → tokens 降得比墙钟快 →
   比值上升。所以它只能和 `wallMsPerTask`、`engineOverheadMsPerCall`、`measuredCalls` 同读，
   不能当「越小越好」的单指标；这条已经写进基准 JSON 的 `caliber.efficiency`。
   两档这一对比值都**上升**（heavy 0.840→1.994、typical 3.478→3.640），而 tokens 与绝对墙钟
   在 heavy 档同时下降——这正是它不能单读的表现。
3. **重复字节必须分列才看得清（本刀新加的读数）**：heavy 档改动前 26.06 MB 重复字节里
   **93 % 是每轮原样重发的 system 注入段**（24.35 MB），历史只占 1.71 MB；改动后注入段
   降到 8.42 MB，历史反而涨到 3.17 MB。历史涨不是改动带坏的——改动前那种形状每轮把历史
   折进摘要（收尾携带消息数只剩 8 条），**该被重复的部分被压掉了才显得历史很干净**；
   改动后历史正常留在窗口里（携带 12 条）。这句因果是**从计数量推出来的解释**（依据＝携带消息数
   8 vs 12、摘要调用 103 vs 21），没有单独做隔离实验去证，读时按解释、不按实测。同理，heavy 档 `engineOverheadMsPerCall`
   29.1 → 54.7 ms 也不该读成「改慢了」：分母少了 82 次几乎不干活、只睡 65 ms 的摘要调用。
4. **同配置复跑的墙钟会动，计数量不会**：`BENCH_INJECTION=heavy BENCH_CAPS=on` 这一档连跑两次
   （10:26 与 10:34，日志 `_w7-bench/heavy_on_run1.log` / `run2.log`）墙钟 18,199 → 14,959 ms
   （−17.8 %），而 tokensPerTask（856,660）、请求体总量（13,706,570 B）、重复占比（0.8455）、
   摘要调用（21）**一字不差**；typical 那两档反而很稳（16,353/16,329、16,702/16,729，差 0.2 %）。
   所以：引用本节按「计数量是确定值，毫秒按量级＋噪声读」，七个窗口同机并行时别拿单个毫秒数下结论。

### 8.5 这一节没覆盖的

- **残留重复的大头仍在注入段本身**。改动后 heavy 档 11.59 MB 重复字节里 8.42 MB（73 %）
  还是每轮重发的 system 段——总量上限只能把它**变小**，不能让它**只发一次**。要做到后者得动
  主会话的携带方式（同一份注入只首轮全文、后续带引用，或吃上游的 prompt cache），
